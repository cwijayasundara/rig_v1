# Security model

rig makes a coding agent follow a process. It is not a sandbox. Read this before relying on it for an enterprise repo.

## What is a boundary and what is not

| Layer | What it gives you | Can the model get around it? |
|---|---|---|
| **CI (`rig-check`) + branch protection + CODEOWNERS** | The trust boundary. The checker and config come from the base branch. A PR that adds or edits an `approval.json` or waiver rows fails unless someone other than the PR author approved the current head commit. Every PR from this repository also gets the `ai-review` job: a clean-context code review and a security review, each briefed from the base branch, failing on a critical or high item under `## Findings` (fork PRs have no secrets and skip it, so a person reviews them); make it a required check. Each PR's risk tier (0, 1 or 2, from the base branch's `risk` config, the diff and the change record; the base's and head's `## Access` rows together) is printed with its reasons; with `risk.enforce: true` on the base, every PR needs an approving review of its head commit from someone other than the author (or the lead override), not only PRs that add approval or waiver rows. Two reviewers for tier 2 or risky paths is a branch-protection or ruleset setting, never rig's. The one alternative is the lead override: a PR author listed in the base branch's `humanApproval.selfApprovers` passes when this run's `ai-review` job and `lead-override` job (paused on the `rig-lead-override` Environment until its required reviewer clicks approve in the web UI) both succeeded on the head commit. | No, if branch protection requires `rig-check` and a code-owner review, and dismisses stale approvals. |
| Hooks (`hooks/hooks.json`) and settings `permissions` | Fast, local feedback: the hooks check each edit and each turn; the template's deny rules keep the Edit and Write tools off evidence files and `.env`, and its ask rules make a person confirm edits to `sensors.json`, `rules.json`, and `.claude/settings.json`. No hook runs on Bash. | **Yes.** Permission rules cover the file tools, not Bash, so a script the model writes and runs can still write a file. Treat them as guardrails, not locks. The template allows `node --disable-warning=ExperimentalWarning .rig/bin/sdlc.ts *` so subagents can record test runs without prompting; `run -- "<command>"` runs any command, including one that sets `SDLC_HUMAN=1`, so local approvals and waivers are not a boundary (CI requires an independent review of every row a PR adds). Edits to `.rig/bin/**` still ask. |
| Managed settings (`templates/managed-settings.json`) and the production gate (`templates/production-gate.sh`) | The platform team's layer: engineers cannot edit or override it. The template is the playbook's p.42 example plus rig's own rules, rig force-enabled (`enabledPlugins` `rig@<marketplace>`, so its hooks survive `allowManagedHooksOnly`), and the p.41 gate as the only managed hook. The gate blocks a Bash command that names `deploy` and the production environment (`RIG_PRODUCTION_ENV`) unless `RELEASE_APPROVAL` is set, and logs each matching decision to `.rig/gates.jsonl` (no command text). | The rules and hooks, no. The gate is a text match: a command that spells deploy another way, or a script that deploys, passes it. Pair it with the deploy tool's own approval (MCP scoped per environment). |
| `/rig-approve`, `/rig-waive` | A human decision recorded as a row in `.rig/`. | The row is only a file. CI is what proves a person made it. |
| Git hooks (`.rig/githooks`, wired at session start) | The same checker at `git commit` and `git push`, for any editor, agent or person. They run tracked code at commit and push, so checking out an untrusted branch and committing runs that branch's checker. The opt-out is `node .rig/bin/sdlc.ts hooks uninstall`. | **Yes**, by `--no-verify` or `hooks uninstall`, from a person or the model. They are guardrails; CI plus branch protection remain the boundary. |

## Do these before a team rollout

1. Protect the default branch: require `rig-check`, require code-owner review, **dismiss stale approvals on new commits**, and block direct pushes. Add a `.github/CODEOWNERS` that covers the files that define the rules, so an agent or its operator cannot change what it is judged by:

   ```
   /.rig/              @your-org/platform
   /.claude/            @your-org/platform
   /.github/workflows/  @your-org/platform
   /CLAUDE.md           @your-org/platform
   ```
2. Run agents in Claude Code's sandbox and deploy managed settings so engineers cannot widen them: start from `templates/managed-settings.json` and tailor it (its `$comment` lists what to change). Three things in it are easy to get wrong. A rule there must use `./path`: a `/path` rule anchors at the settings file's own folder, not the repo. Force-enable rig by its full `rig@<marketplace>` ID, or `allowManagedHooksOnly` switches rig's hooks off. `allowManagedPermissionRulesOnly` drops the project's rules, so the managed file carries rig's. Install `templates/production-gate.sh` root-owned at the path the template names (outside every repo, never `.claude/hooks/`, which the model can edit).
3. Keep Bash on a prompted permission mode for unattended fan-out steps.
4. Install from your own fork pinned to a release tag, not from a moving branch.

## Known limits

- The lead override trades the second person for an AI review and a click. Set it up with: the lead as required reviewer of the `rig-lead-override` Environment (leave "prevent self-review" off), the `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` secret, and `actions: read` on the workflow. The label only starts `lead-override`; the Environment click is the human decision, so keep the Environment's reviewer list and the workflow under CODEOWNERS. Adding a login to `selfApprovers` is reported as a `harness-tamper` weakening. Where code-owner review is also required by branch protection, GitHub still blocks the author's own PR, so add the lead to the ruleset's bypass list; rig cannot do that for you. A person with admin rights who owns the Environment can approve their own override: this is accountability (the click and AI review are logged on the run), not separation of duties.

- Permission rules cover the file tools only. A model that writes and runs a script can touch evidence files locally; CI catches forged approvals and waivers, not forged `runs.jsonl` rows on a branch nobody reviews.
- The secrets sensor is pattern based. It misses unusual token formats and skips files over 2 MB or detected as binary.
- The production gate is a text match on the command, as in the playbook. `RELEASE_APPROVAL` is a placeholder for your real approval check (a change-ticket lookup): set in the shell that starts Claude Code, it is the person's assertion, not proof. The p.42 sandbox denies `GITHUB_TOKEN` and limits network domains: `gh` (used by `/rig:pr`) needs github.com, api.github.com and its own login,.
- Any settings layer's `env` can set `RELEASE_APPROVAL`: a committed `.claude/settings.json` with it in `env` switches the gate off for the whole repo. CODEOWNERS on `/.claude/` and the ask rule on `.claude/settings.json` are what stop that; review any `env` change there. When managed settings come from the server (the admin console) rig cannot read them; the template's `RIG_MANAGED_HOOKS_ONLY` env marker tells rig's hooks that `allowManagedHooksOnly` is on, so keep it in whatever you deploy.
- Under the managed template, the sandbox, not the deny list, bounds the network: `sdlc.ts run --` passes the `Bash(curl *)` and `Bash(wget *)` denies. Rules use `./path`, relative to where Claude Code starts, so start sessions at the repo root.
- Two allow rules in the managed template trade control for rig's flows; remove them where the data classification demands. `Bash(node … .rig/bin/sdlc.ts *)` lets `sdlc.ts run -- "<command>"` run any command without a prompt, past the managed deny rules (`Bash(curl *)` and the like); the sandbox's domain list is then what bounds the network. `Bash(git *)` (from p.42) can push to any remote the sandbox reaches. github.com and api.github.com in `allowedDomains` are an egress route to any GitHub repository: keep them only where `gh` must work, and prefer your GitHub Enterprise host.
- Windows is not supported yet: its CI job is red (about ten tests in the `pr` flows use POSIX shell fakes for `gh`), and the end-to-end check runs on Linux. Do not require the Windows job in branch protection until it is fixed.

## Reporting

Report a vulnerability privately to the maintainers (GitHub security advisories on this repository). Do not open a public issue.
