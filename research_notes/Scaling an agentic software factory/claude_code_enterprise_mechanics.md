# Claude Code enterprise mechanics: distributing, governing and running a custom harness (state as of 12 Nov 2026)

Method note: fetched primary docs at code.claude.com/docs (pages return markdown), platform.claude.com. Version numbers quoted are those the docs state. "Gap" = not found/not verified. Items marked [BETA]/[PREVIEW] are labelled so in the docs.

## 1. Distribution: plugins, marketplaces, versioning, scopes, force-enable/restrict

### Takeaway
A harness (skills, hooks, subagents, scripts, MCP) packages as a plugin served from a git-hosted marketplace (`.claude-plugin/marketplace.json`). Admins force-install via managed `extraKnownMarketplaces` + `enabledPlugins`, restrict sources via `strictKnownMarketplaces`/`blockedMarketplaces`, and pin versions per plugin with `ref`/`sha`/`sha256` or an omitted-`version` (commit-SHA) scheme. There is no per-user/group targeting inside one policy and no built-in release channels: use separate marketplaces and separate managed-settings deliveries.

### Cited Findings
- Marketplace = directory/repo with `.claude-plugin/marketplace.json` (required: `name`, `owner`, `plugins`); can be private, list many plugins, and "an administrator can require it on every machine". — [Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)
- Hosting options: GitHub, other git host (GitLab/Bitbucket/GHES; full URL needed, `owner/repo` shorthand always means github.com), hosted `marketplace.json` URL, shared-filesystem directory. Pin catalog branch/tag with `#<ref>` on add. — [Host and maintain a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- Plugin source types per entry: relative path, `github`, `url` (any git), `git-subdir` (sparse checkout of a monorepo subdir), `npm` (installed without running install scripts), `archive` (zip over HTTPS, `sha256` pin), `command` (runs a command on the user's machine; v2.1.229+). — [Marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md)
- Pinning: `github`/`url`/`git-subdir` sources take `ref` (branch/tag) and `sha` (full 40-char commit); if both set, `sha` is checked out. `archive` pins via `sha256` and Claude Code refuses a mismatching download. `npm` takes `version` (version/range/dist-tag). — [Marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md)
- Versioning/update rule: user gets a new copy only when the plugin's computed version changes; version comes from `plugin.json` first, then the marketplace entry. Either bump `version` each release or omit it (then users track commits). Setting `version` in both places: `plugin.json` wins silently; `validate` warns. Pushing new commits without a version bump leaves users on cached copy. — [Host and maintain a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- Plugins loaded in place from a local-path marketplace ignore `version` and load current files each session start. — same page.
- Auto-update is OFF by default for a marketplace; `marketplace.json` has no field to enable it. A user toggles it in `/plugin`, or admin sets `"autoUpdate": true|false` on the managed `extraKnownMarketplaces` entry (then user toggle is refused with "Auto-update for '<name>' is set by..."). — [Host and maintain](https://code.claude.com/docs/en/plugins/host-marketplace.md); [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org.md)
- Fleet-wide off: managed `env` `DISABLE_AUTOUPDATER=1` (also stops Claude Code's own updates); add `FORCE_AUTOUPDATE_PLUGINS=1` to keep plugin updates while stopping binary updates. `command`-source plugins re-run each session regardless. — [org.md](https://code.claude.com/docs/en/plugins/org.md)
- Force-install pattern (managed settings): `extraKnownMarketplaces` {name: {source:{source:"github",repo:"your-org/your-marketplace"}, autoUpdate:true}} + `enabledPlugins` {"plugin@marketplace": true}. Installed at start of user's next session; user disabling at own scope does not stop load (managed wins). `false` in managed `enabledPlugins` blocks a plugin at every scope and hides it. — [org.md](https://code.claude.com/docs/en/plugins/org.md)
- Restriction keys (all managed): `strictKnownMarketplaces` (allowlist; alias `allowedMarketplaces`; `[]` blocks everything incl. official), `blockedMarketplaces` (checked first), `disableSideloadFlags` (rejects `--plugin-dir`, `--plugin-url`, `--agents`, SDK `plugins` option, `CLAUDE_CODE_PLUGIN_DIRS`), `disableCommandPluginSources`, `strictPluginOnlyCustomization` (blocks skills/agents/hooks/MCP from user & project sources; `true` or array of `skills`,`agents`,`hooks`,`mcp`), `syncClaudeAiPlugins`/`syncClaudeAiSkills`, `pluginSuggestionMarketplaces`, `pluginTrustMessage`. Allowlist entry types: `github` (incl. `your-org/*` wildcard, v2.1.223+), `git`, `url`, `file`, `directory`, `hostPattern`, `pathPattern`, `skills-dir`. — [org.md](https://code.claude.com/docs/en/plugins/org.md)
- Allowlist does NOT restrict individual plugins inside an allowed marketplace (block with `enabledPlugins:false`), cannot hide `/plugin`, and does not gate `--plugin-dir` (needs `disableSideloadFlags`). Every plugin key applies to all users who receive the settings: no per-user targeting. — [org.md](https://code.claude.com/docs/en/plugins/org.md)
- Scopes for installs: `claude plugin install <plugin>@<marketplace> --scope project|user|local`; repo `.claude/settings.json` `extraKnownMarketplaces` apply only after workspace trust (interactive) or previously-trusted folder (`-p`); setting `enabledPlugins` in the repo does not itself install the plugin. — [org.md](https://code.claude.com/docs/en/plugins/org.md); [settings](https://code.claude.com/docs/en/settings)
- Private repos: Claude Code has no git token of its own; runs `git` non-interactively using the machine's credentials (SSH agent, credential helper; `gh auth setup-git`). Background auto-update with helper needing a prompt fails quietly; on failure it re-clones unless `CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE=1`. `GITHUB_TOKEN` alone doesn't authenticate unless a credential helper reads it. — [host-marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- No-git-account distribution: `archive` sources with `headers`/`headersHelper` (v2.1.238+; entries using `headersHelper` need `"strict": false` and user accepts the command per install); org-sync via claude.ai Organization settings > Plugins & skills (uses org's GitHub/GitLab connection; repo must be private/internal; rejects plugins with top-level `bin/`). — [host-marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- Seeding for containers/CI: build with `CLAUDE_CODE_PLUGIN_CACHE_DIR=/opt/claude-seed claude plugin marketplace add ...; claude plugin install ...`, run with `CLAUDE_CODE_PLUGIN_SEED_DIR`; seed is read-only, autoUpdate forced off, seed entries override user entries; plugins still need `enabledPlugins`. In `-p`/CI installs happen in background; `CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1` waits. Private marketplace in CI: `GH_TOKEN` + `gh auth setup-git`. — [org.md](https://code.claude.com/docs/en/plugins/org.md)
- Release channels: not a concept; host two marketplaces (different `name`) pointing at different refs, assign per group via separate endpoint-managed settings, a Claude apps gateway policy per group, or (Enterprise) per-group server-managed config; group configs don't merge with org-wide. — [org.md](https://code.claude.com/docs/en/plugins/org.md); [host-marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- Rename/removal: `renames` map, `forceRemoveDeletedPlugins: true` uninstalls removed plugins at session start (managed-installed plugins stay). Dependencies with semver ranges resolve against `<plugin>--v<version>` git tags; cross-marketplace deps need `allowCrossMarketplaceDependenciesOn`. — [host-marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)
- Git submodule handling: only submodules holding plugin files are fetched (v2.1.295+). — [Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)
- Plugin hook/MCP caveat: hooks in plugins enabled by users are not trusted under `allowManagedHooksOnly` (see section 2); entry-level `hooks` must be inline objects. — [org.md control matrix](https://code.claude.com/docs/en/plugins/org.md); [marketplace-reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md)
- Plugin audit: OTel events `claude_code.plugin_installed` and `plugin_loaded`; Enterprise Analytics API `GET /v1/organizations/analytics/plugins` (per-plugin/day installs and invocations, group by user/RBAC group); third-party plugin names redacted unless `OTEL_LOG_TOOL_DETAILS=1`. — [org.md](https://code.claude.com/docs/en/plugins/org.md)
- Reserved marketplace names (e.g. `claude-plugins-official`) cannot be used for own marketplaces. — [marketplace-reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md)

### Inferences
- For 33k engineers: one org marketplace repo + managed `enabledPlugins` + `strictKnownMarketplaces` (org wildcard + official) + `disableSideloadFlags`; pin each plugin with `sha` (or `archive`+`sha256` from an internal artifact registry) so rollout is a reviewed PR to the marketplace repo, not a mutable branch.
- Different client environments needing different harness versions = separate marketplaces/managed-settings per device group; the docs give no finer targeting.
- Private-repo auto-update is fragile on laptops with prompting credential helpers; archive/registry or seed images are more reliable at scale.

### Gaps
- No documented plugin-level signing beyond `sha`/`sha256` pins. Not found.
- Exact semantics of `version` computed from commit SHA when omitted not read beyond the statement above (docs "Plugin loading reference" `/plugins/loading.md` not fetched).

## 2. Governance: managed settings, MDM, permissions, hooks, sandbox, MCP, models, audit

### Takeaway
Managed settings are the top precedence tier and can be delivered four ways (server-managed from claude.ai console [Team/Enterprise], MDM plist/HKLM, files incl. `managed-settings.d/`, HKCU low-trust). Policy covers permissions, hooks, sandbox, MCP, plugins, models, login, provider, version floors. Audit comes from OTel, the Compliance API (Enterprise) and an optional gateway.

### Cited Findings
- Scopes/precedence (high to low): Managed > command line (`--settings`) > project local > shared project > user. List keys (e.g. `permissions.allow`) merge across scopes. `model` managed is a default not a lock; locks are `availableModels`/`deniedModels`. — [Settings](https://code.claude.com/docs/en/settings)
- Delivery mechanisms and paths: server-managed (admin console; fetched at start, polled hourly); macOS configuration profile domain `com.anthropic.claudecode`; Windows `HKLM\SOFTWARE\Policies\ClaudeCode` value `Settings` (JSON as REG_SZ); files `/Library/Application Support/ClaudeCode/managed-settings.json` (macOS), `/etc/claude-code/managed-settings.json` (Linux/WSL), `C:\Program Files\ClaudeCode\managed-settings.json` (Windows), plus `managed-settings.d/` drop-ins and `managed-mcp.json`; HKCU registry is user-writable fallback. MDM/OS policy re-checked every 30 minutes. — [Deploy managed settings](https://code.claude.com/docs/en/managed-settings.md); [Admin setup](https://code.claude.com/docs/en/admin-setup.md)
- By default only ONE managed source applies (first with a policy key: server > MDM > file); `managedSourcesBehavior: "merge"` composes all; `policyHelper` executable can compute policy at startup. — [managed-settings](https://code.claude.com/docs/en/managed-settings.md); [org.md](https://code.claude.com/docs/en/plugins/org.md)
- Tamper resistance: plist/HKLM need admin to write; a local admin can edit the file source, hence redeploy by MDM. Server-managed settings do not reach Bedrock/Vertex/Foundry sessions or sessions with `ANTHROPIC_BASE_URL` to non-Anthropic host. — [managed-settings](https://code.claude.com/docs/en/managed-settings.md); [Feature availability](https://code.claude.com/docs/en/feature-availability.md)
- Invalid managed JSON: Claude Code refuses to start; a single bad entry is dropped (some keys fail closed). `requiredMinimumVersion`/`requiredMaximumVersion` refuse to start outside range (fail open on invalid value); `minimumVersion` blocks downgrades. — [managed-settings](https://code.claude.com/docs/en/managed-settings.md); [Admin setup](https://code.claude.com/docs/en/admin-setup.md)
- Enforcement keys (Admin setup table): `permissions.allow/deny`, `allowManagedPermissionRulesOnly`, `permissions.disableBypassPermissionsMode`, `permissions.defaultMode`, `permissions.disableAutoMode`; `sandbox.enabled`, `sandbox.network.allowedDomains`; `allowedMcpServers`, `deniedMcpServers`, `allowManagedMcpServersOnly`, `managedMcpServers`/`managed-mcp.json`; `allowManagedHooksOnly`, `allowedHttpHookUrls`; `forceLoginMethod`, `forceLoginOrgUUID`; `allowedProviders` (v2.1.285+); `availableModels`, `enforceAvailableModels`, `maxEffortLevel`; `disableAgentView`, `processWrapper`; telemetry opt-out via `env` `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`; managed policy CLAUDE.md file. — [Admin setup](https://code.claude.com/docs/en/admin-setup.md)
- Array settings in `permissions.allow/deny` merge from all sources so developers can extend but not remove managed entries; `fallbackModel`, `availableModels`, `modelPicker` managed value replaces. — [Admin setup](https://code.claude.com/docs/en/admin-setup.md)
- Hooks that cannot be bypassed: `allowManagedHooksOnly` restricts which hooks run (does not trust hooks from user-enabled plugins); `strictPluginOnlyCustomization:["hooks"]` blocks user/project hooks; managed-settings `hooks` themselves are enforceable. Full effect list is in settings-reference "what runs under allowManagedHooksOnly" (not fetched). — [org.md control matrix](https://code.claude.com/docs/en/plugins/org.md); [Admin setup](https://code.claude.com/docs/en/admin-setup.md)
- Hooks in `-p` mode: without `--bare`, `claude -p` runs project `.claude/settings.json` hooks and `.mcp.json` servers even in an untrusted folder (no trust dialog in `-p`). — [Headless](https://code.claude.com/docs/en/headless.md)
- Exceptions where a stricter lower-scope value beats managed: e.g. `permissions.blockReadsOutsideWorkingDirectories`, `disableClaudeAiConnectors`, `maxEffortLevel` (lowest cap wins). — [Settings](https://code.claude.com/docs/en/settings)
- Sandboxing: OS-level filesystem/network isolation with domain allowlist, complements permission rules (denying WebFetch doesn't stop `curl` if Bash is allowed). Settings `sandbox.enabled`, `sandbox.network.allowedDomains`. — [Admin setup](https://code.claude.com/docs/en/admin-setup.md)
- Model governance: managed `availableModels`/`enforceAvailableModels`; on Teams/Enterprise via claude.ai: org model restrictions, org default model, org effort limits (server-side; do NOT reach Bedrock/Vertex/Foundry/Claude Platform on AWS, where managed settings are the path). For third-party providers pin versions with `ANTHROPIC_DEFAULT_{FABLE,OPUS,SONNET,HAIKU}_MODEL`. — [Admin setup](https://code.claude.com/docs/en/admin-setup.md); [Enterprise deployment overview](https://code.claude.com/docs/en/third-party-integrations.md)
- Audit: Compliance API `GET /v1/compliance/activities` (Enterprise per plan table) lists 590+ activity types incl. `ccr_session_*`, `claude_code_review_*`, `claude_plugin_*`, `claude_skill_*`, `mcp_server_*`, `marketplace_*`, `sso_*`, `scim_*`, `rbac_role_*`, `org_hipaa_*`, `org_ip_restriction_*`. — [Compliance API ref](https://platform.claude.com/docs/en/api/compliance); plan matrix in [Feature availability](https://code.claude.com/docs/en/feature-availability.md)
- Request-level audit/data-sensitivity routing: Anthropic recommends a gateway: self-hosted Claude apps gateway ("per-request audit log with IdP identity") or another LLM gateway; gateway sessions are not eligible for HIPAA configuration. — [Admin setup](https://code.claude.com/docs/en/admin-setup.md)
- OTel `managed_settings_resolved` event (needs `OTEL_LOG_MANAGED_SETTINGS=1`) and `tool_decision` events (source: config/hook/user_*) give policy-effect evidence. — [Monitoring](https://code.claude.com/docs/en/monitoring-usage)

### Inferences
- Because only one managed source applies by default, mixed fleets (some users on claude.ai seats, some on Bedrock/gateway) need a file/MDM fallback plus server-managed, and `managedSourcesBehavior: "merge"` must be deliberately set.
- Client-side enforcement is only as strong as device control; for clients where engineers have local admin, gateway-side controls (allowedProviders pinned to a gateway) are the harder boundary.

### Gaps
- Full text of `allowManagedHooksOnly` effect list, sandbox settings page, and permissions page not fetched.
- No documentation found (in what I fetched) of a dedicated Claude Code-specific audit log of prompts for Teams/Enterprise beyond Compliance API activities and OTel (content logging is opt-in).
- Compliance API plan requirements/retention not readable from truncated fetch; plan table says Enterprise only.

## 3. Running autonomously: -p, Agent SDK, GitHub Actions/GitLab, cloud sessions, scheduled tasks, Managed Agents

### Takeaway
For "PRD in, PR out" with human gates: `claude -p`/Agent SDK in your own CI (works on every provider, you control runners and gates) or the GitHub Action are the GA, provider-agnostic options; cloud sessions and scheduled tasks are subscription-only and [PREVIEW]; Managed Agents is [BETA] API-only, not ZDR/HIPAA eligible. Human approval gates map naturally onto PR review/branch protection, `plan` permission mode, and separate pipeline stages.

### Cited Findings
- `claude -p` is "the Agent SDK via the CLI"; also Python/TypeScript packages with structured output and tool-approval callbacks. Exit 0 success/non-zero failure; `--output-format json|stream-json`; JSON includes `total_cost_usd` (client-side estimate); `--json-schema` for structured output; `--max-budget-usd`; `--max-turns`; `--resume`/`--continue`. — [Headless](https://code.claude.com/docs/en/headless.md)
- `--bare` skips auto-discovery of hooks, skills, plugins, MCP, CLAUDE.md; "recommended for scripted and SDK calls, and will become the default for -p in a future release"; bare mode never reads OAuth/keychain (needs `ANTHROPIC_API_KEY` or `apiKeyHelper`; Bedrock/Vertex/Foundry creds still work); hooks from `--settings` or flag-loaded plugins do NOT run in bare mode, so don't use bare for runs needing the harness hooks. — [Headless](https://code.claude.com/docs/en/headless.md)
- Unattended permissions: `--permission-mode dontAsk` denies anything needing a prompt; `--permission-prompts none` (v2.1.259+); non-interactive `-p` starts in Manual mode when nothing sets a mode (v2.1.302+); `auto` mode uses a classifier. — [Headless](https://code.claude.com/docs/en/headless.md)
- CI gate for harness load: `system/init` event lists `plugins`, `plugin_errors`, `mcp_servers`, `mcp_server_errors`; fail the job on non-empty error arrays. — [Headless](https://code.claude.com/docs/en/headless.md)
- GitHub Action `anthropics/claude-code-action@v1`: interactive mode (@claude mention) vs automation mode (`prompt` input; any GitHub event incl. cron); `plugin_marketplaces` + `plugins` inputs install plugins; prompt can be `/plugin-name:skill-name`; `claude_args` passes any CLI flag (`--max-turns`, `--model`, `--allowedTools`); needs write access for triggering users; bots rejected unless in `allowed_bots`. — [GitHub Actions](https://code.claude.com/docs/en/github-actions.md)
- Action auth: `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN` (tied to the person's subscription; docs recommend API key for org-wide shared secret), or workload identity federation via GitHub OIDC (`anthropic_federation_rule_id` `fdrl_...`, `anthropic_organization_id`, service account `svac_...`); Bedrock/Vertex/Foundry via `use_bedrock|use_vertex|use_foundry` with OIDC. — [GitHub Actions](https://code.claude.com/docs/en/github-actions.md)
- Official Claude GitHub App has a fixed broad permission set (Actions, Contents, PRs, Workflows, Repository creation, etc.); no subset acceptable; org can create a custom GitHub App (Contents, Issues, PRs) for the Action only. Org rollout: org-level app install, org-level secret, reusable workflow. — [GitHub Actions](https://code.claude.com/docs/en/github-actions.md)
- Cost controls named for Action: `--max-turns`, workflow timeouts, concurrency controls. — [GitHub Actions](https://code.claude.com/docs/en/github-actions.md)
- Action availability by provider: GitHub Actions not on Claude Platform on AWS; GitLab CI/CD not on Foundry. — [Feature availability](https://code.claude.com/docs/en/feature-availability.md)
- Cloud sessions (Claude Code on the web), cloud scheduled tasks, Code Review, Remote Control, Chrome ext: require claude.ai account; not reachable with Console API keys or cloud-provider credentials alone. Disabled under ZDR (cloud sessions). — [Admin setup](https://code.claude.com/docs/en/admin-setup.md); [ZDR](https://code.claude.com/docs/en/zero-data-retention.md)
- Cloud sessions run in a cloud environment on a fresh clone; only server-managed settings reach them (not MDM/file); user/local settings not read; marketplaces and plugins declared via `enabledPlugins`/`extraKnownMarketplaces` "still don't load in a cloud session" (Anthropic-hosted multi-repo statement; see cloud-environments "what carries over"). Admins define org-shared environments (network access level, env vars, setup script). Self-hosted environments exist for cloud sessions. — [Settings](https://code.claude.com/docs/en/settings); [Admin setup](https://code.claude.com/docs/en/admin-setup.md)
- Scheduled tasks (formerly routines) [PREVIEW, "Behavior, limits, and the API surface may change"]: cloud saved config (prompt + repos + connectors); triggers: schedule, API (`/fire` POST with per-task bearer token, beta header `experimental-cc-routine-2026-04-01`), GitHub events; Pro/Max/Ultra/Team/Enterprise; belong to an individual's claude.ai account, not shared with teammates, actions appear as that user; pushes to `claude/`-prefixed branches by default; branch protection controls pushing; sessions start in auto mode; limits: 100 scheduled runs/hour per account, 30/hr per task for Run now/API fires, 100/hr API fires per account; no overage on these hourly limits; runs draw subscription usage (usage credits can overflow). Can run in an org self-hosted environment. — [Scheduled tasks](https://code.claude.com/docs/en/routines.md)
- Managed Agents [BETA, header `managed-agents-2026-04-01`]: hosted harness: Agent (model, system prompt, tools, MCP, skills) + Environment (Anthropic cloud sandbox or self-hosted sandbox) + Session + Events; stateful, server-side history; scheduled deployments; self-hosted Managed Agents service exists; supported on Claude API, Claude Platform on AWS, Claude Models on Google Cloud (Anthropic managed); NOT eligible for ZDR (except self-hosted) or HIPAA; MCP tunnels and "dreaming" are limited research preview. Search snippet cites create limit 60/min, read 600/min (reference page not fetched). — [Managed Agents overview](https://platform.claude.com/docs/en/managed-agents/overview.md); rate-limit figure from search snippet only
- Managed Agents consumes Skills in the agent definition; whether Claude Code plugins/hooks/marketplaces are consumed by it was NOT established.

### Inferences
- Best fit for gated pipeline: orchestrator (GitHub Actions/GitLab/own scheduler) invoking `claude --bare -p` or Agent SDK per stage, loading harness via seeded plugin dir + managed settings (not `--bare`, if hooks matter) ; gates = PR review/required checks/branch protection + `plan` mode stage outputs persisted as artifacts. Cloud scheduled tasks are per-person and preview, so poor fit as an org pipeline backbone; Managed Agents is attractive for hosted long-running runs but requires rebuilding the harness as agent/skills definitions and is not ZDR-eligible.
- Hooks/bare-mode interaction is a trap: if the harness enforces gates via plugin hooks, `--bare` will silently skip them.

### Gaps
- GitLab CI/CD page, Agent SDK docs, cloud-environments page and Code Review page not fetched.
- No documented concurrency/rate figure for Agent SDK itself; throughput governed by API rate limits (section 5).
- Whether Managed Agents can load Claude Code plugin hooks/subagents: not found.

## 4. Deployment options: seats vs API vs Bedrock/Vertex/Foundry; gateways; residency; ZDR; feature loss

### Takeaway
Teams/Enterprise seats are Anthropic's default recommendation and the only path to server-managed settings, analytics dashboard/API, cloud sessions, routines, Code Review, Compliance API. Bedrock/Vertex ("Google Cloud's Agent Platform")/Foundry keep local CLI/SDK/plugins/hooks/MCP/sandbox/OTel/managed-settings file but lose everything tied to claude.ai.

### Cited Findings
- Provider comparison (billing/regions/auth/cost tracking/enterprise features): Teams/Enterprise per-seat (+PAYG); Console PAYG; Bedrock IAM/CloudTrail; Claude Platform on AWS (AWS Marketplace billing, Claude API features); Vertex/Agent Platform IAM/Cloud Audit Logs; Foundry RBAC/Azure Monitor. Prompt caching enabled by default on all (Bedrock support varies by model). — [Enterprise deployment overview](https://code.claude.com/docs/en/third-party-integrations.md); [Feature availability](https://code.claude.com/docs/en/feature-availability.md)
- Works on every provider: CLI, Agent SDK, IDE extensions, subagents, hooks, commands, skills, CLAUDE.md, plugins, MCP, checkpoints, sandboxing, Workflows, OTel, managed settings file. — [Feature availability](https://code.claude.com/docs/en/feature-availability.md)
- Not on Bedrock: cloud sessions, scheduled tasks (`/schedule`; use `/loop`), Code Review, Remote Control, Artifacts, web search, fast mode, Advisor, Channels, analytics dashboard, server-managed settings. Alternatives: GitHub Actions/GitLab CI. Foundry additionally lacks GitLab CI/CD. Vertex has partial web search/fast mode. Claude Platform on AWS lacks GitHub Actions. — [Feature availability](https://code.claude.com/docs/en/feature-availability.md)
- Plan matrix: Server-managed settings Team+Enterprise; SSO Team+Enterprise; SCIM, Compliance API, Enterprise Analytics API Enterprise only; Code Review Team/Enterprise; Cloud sessions on Enterprise require premium or Chat+Claude Code seat; ZDR Enterprise qualified only. — [Feature availability](https://code.claude.com/docs/en/feature-availability.md)
- Console (API) path: Console sign-in/API key; Claude Code workspace auto-created for cost tracking; workspace spend and rate limits; Claude Code Analytics API. Server-managed settings from a claude.ai org don't reach Console-key sessions. — [Costs](https://code.claude.com/docs/en/costs.md); [Feature availability](https://code.claude.com/docs/en/feature-availability.md)
- Gateways: any gateway exposing a supported API format works; Anthropic "doesn't endorse, maintain, or audit third-party gateway products, and doesn't support routing Claude Code to non-Claude models"; env vars `ANTHROPIC_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL`, `ANTHROPIC_AWS_BASE_URL`, `ANTHROPIC_VERTEX_BASE_URL`, `ANTHROPIC_FOUNDRY_BASE_URL`; gateway must forward new Claude Code features; pin with `allowedProviders:["customEndpoint"]` + managed `env` (v2.1.285+). With `ANTHROPIC_BASE_URL` to non-Anthropic host Claude Code turns off Remote Control and server-managed settings. — [LLM gateways](https://code.claude.com/docs/en/llm-gateway.md); [Feature availability](https://code.claude.com/docs/en/feature-availability.md)
- Claude apps gateway: Anthropic's self-hosted gateway adding IdP sign-in in front of Bedrock, Claude Platform on AWS, Vertex, Foundry or Anthropic API; per-request audit log with IdP identity, OTLP metrics, per-user spend limits, can deliver server-managed-style settings policies per group; some commands (`/design-sync`, `/import`) unavailable through it. ## 6. Testing a harness: `claude plugin eval` and alternatives

### Takeaway
`claude plugin eval` (Claude Code v2.1.269+) is the first-party regression/CI tool: cases = prompt + graders, run in fresh isolated non-interactive sessions, 3 runs per case by default, with a no-plugin baseline arm and a score gate for CI. Cost is real model calls.

### Cited Findings
- Definition and use cases (measure reliability, catch regressions "when you change the plugin or a new model is released", see plugin contribution vs none); suite in plugin `evals/` dir (case = dir with `prompt.md` and/or `case.yaml` plus `graders/*.md`); `claude plugin eval init` generates suite interactively; requires v2.1.269+ and real model credentials. — [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- Scoring: each case runs 3 times by default; run score = fraction of graders passed (weights optional); case score = mean; with default baseline, runs ~ cases x runs with plugin plus same number without plugin, plus three short judge calls per `llm`/`baseline` grader per run. `--ablation none` halves cost; `--runs 1`, `--case <name>`, `--judge-model`, `--tag`, `--allow-tools`, `--json [path]`, `--scaffold` exist. Output table columns CASE/WITH/W/OUT/Δ/RUNS/COST/NOTES; HTML and JSON reports. — [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- Six grader types: `regex`, `tool_used`, `tool_order`, `llm` (judge model rubric), `baseline`, and file/created-style checks (full list in "Grader types", not fully read); "There are no custom-code graders." Mock MCP servers supported (static or `type: agent` judge-answered). `scaffold_script` seeds fixtures but runs outside the sandbox as you. — [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- Runs execute in isolated sessions with only the plugin loaded; non-interactive per headless docs. Custom eval dir via `"experimental": {"evals": "quality/evals"}` in `plugin.json`. — [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- Complementary tools: `claude plugin validate <path>` (schema/syntax, not behaviour); skill-creator plugin evals (`evals/evals.json`, different format); `--output-format stream-json` `init` event checks for `plugin_errors`; third-party skill testers exist (e.g. SkillCI) with unknown quality. — [plugin-evals](https://code.claude.com/docs/en/plugin-evals.md); [Headless](https://code.claude.com/docs/en/headless.md); search result list (unverified third parties)
- Shipping date "September 11, 2026 (v2.1.269)" appears only in a third-party search snippet; docs confirm only the v2.1.269 minimum. — [aicatchup summary](https://aicatchup.com/news/claude-code-plugin-evals-regression-testing) (secondary, unverified)
- Is `claude plugin eval` labelled beta? The page header lacks an explicit beta note in what was read; plugin.json key lives under `"experimental"`. Treat as potentially unstable. Not confirmed.

### Inferences
- A harness comprising skills + hooks + subagents can only be partly covered: graders see replies, tool calls, files; no custom code graders, so hook/gate enforcement is best tested by `tool_used`/`tool_order` + file graders or by separate script tests (what rig's own repo does with `npm test` is outside Anthropic tooling).
- Model upgrades are the main regression source; pin models (`ANTHROPIC_DEFAULT_*_MODEL`) and run evals in CI on both marketplace PRs and model-version changes.

### Gaps
- Exit codes / CI-gate flags (threshold option) not read from the persisted page; the docs advertise "gate CI on the score" but exact flag names unread here.
- No evidence found of evals for multi-turn/multi-stage pipelines beyond `history_file` seeding.
