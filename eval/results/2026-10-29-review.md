## Notes on this run (verification evidence, item 1)

- 72 calls (12 cases x 2 models x 3 runs, clean arm only), no failures, $5.61: Sonnet 5.5 $1.82, Opus 5.5 $3.79.
- **Gate not met.** The proposal's gate was hard recall below 100% for at least one reviewer. Both models caught every
  hard case in every run, so the eval still cannot rank reviewers. It decides nothing about Sonnet against Opus or one
  reviewer against finders + verifier.
- **Precision held.** 0 findings on the three clean controls in 9 runs each, the two baited ones included: on this brief,
  neither model raised findings against hypothetical concerns. Extra findings on defect runs: 0.52 (Opus), 0.56 (Sonnet).
- **Catches were not read.** Rows kept counts only, and the patterns are loose (any `cache` finding on `cart.js` counts
  for lines-cache-stale), so some catches may be a different finding that happens to match. Rows now keep the review
  text (`text`) so the next run can be audited.
- **Why the hard cases were easy:** the whole source tree is about 100 lines and sits in the prompt; set-qty-edges' spec
  names the qty-0 edge outright; every defect breaks a numbered B-line the reviewer is told to check. Difficulty here
  came from the kind of defect, but a reviewer's misses in practice come from scale and from defects no spec line names.
- **What would discriminate:** a real codebase in the thousands of lines (shop_app, or this repo's own `scripts/`); a
  defect inside a multi-file diff of a few hundred lines; defects no B-line names (money rounding, an error path, a
  race in `server.js`); and real reverts mined from shop_app history.
- Equal recall at half the price is a hint for Sonnet on small, spec-explicit diffs, not evidence: the eval is
  saturated, so it cannot show where the two differ.

Audit of every row (each review's text read, not just the pattern match):

- **Every catch is the seeded bug,** named in the Findings section with the right line and the right reason (for example
  "`StorageError` subclasses `CartError`, so `EXIT_STORAGE` is unreachable", and the tests loosened to `!= 0`). The loose
  patterns did not inflate any score.
- **cli-empty-file-arg is a triage call, not a blind spot.** All 6 reviews saw `if file:` ignoring `--file ""`; Opus filed
  it as a finding once and deferred it 2 times, and Sonnet deferred it 3 times. The spec is silent on empty values, and the
  correct control has the same grey area (`CART_FILE=""` becomes `Path("")`, which reviewers of cli-ok also deferred). The
  case does not separate the models; it measures where each puts the bar.
- **Sonnet's one false finding** (cli-ok run 3): `print(line)` after the save raises on a stdout that cannot encode the sku,
  so the command fails although the cart changed. It is real but marginal; Opus deferred the same point.
- **Extra findings per defect run:** Opus 0.22, Sonnet 0.06.
- **The one real difference: unseeded bugs in the code around the diff.** `storage.py` `save` runs `_fsync_directory` inside
  the `try` after `os.replace`, so a directory fsync failure raises "cannot be written" after the file was already
  replaced (shop_app cart-core, at 26f1105). Opus mentioned it in 17 of 24 cart reviews, Sonnet in 6 of 24. That bug was
  not seeded, so no score counts it.

**Gate:** hard recall is 94% (Opus) and 91% (Sonnet), so it is below 100% as the proposal asked, but only because of the
ambiguous empty-file case. On the five clear seeded bugs both models score 100%. Single seeded bugs in a 262-line diff on
900 lines of code, with the spec in the prompt, are still within both models' reach. The eval does not justify paying
Opus over Sonnet for the PR review of diffs like this. Opus does read further into the surrounding code; whether that is
worth 2.5x the price needs cases scored on unseeded, pre-existing bugs.
