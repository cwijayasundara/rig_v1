# Devin (Cognition): wiki, memory, decomposition, and what a thin Claude Code harness should take

## 1. DeepWiki

What is generated [documented]: architecture diagrams, docs, source links, summaries per repo; viewable at app.devin.ai/wiki; auto-generated when repos are connected. https://docs.devin.ai/work-with-devin/deepwiki
- Public free version: change github.com to deepwiki.com; >50,000 top public repos indexed; private repos need a Devin account. https://cognition.com/blog/deepwiki
- Planning: default is "cluster-based planning". A committed `.devin/wiki.json` bypasses it and creates exactly the listed pages. Schema: `repo_notes[]` (content, author?) and `pages[]` (unique title, purpose, optional parent, page_notes). Limits: 30 pages (80 enterprise), 100 notes total, 10,000 chars/note. Regenerate after commit. [documented] https://docs.devin.ai/work-with-devin/deepwiki
- Freshness: the docs state NO refresh schedule or change detection. Regeneration is manual after steering edits. [documented that it is unspecified]
- Cost [documented]: Low effort free (default; enterprise always Low); Medium ~5-10 ACUs per wiki; High ~20-40 ACUs per wiki. Effort set per org, overridable per repo. Same page.
- Consumption by agents [documented]:
  - Ask Devin uses wiki info plus code search for cited answers; Plan mode produces a context-rich prompt and can start a session from the conversation. https://docs.devin.ai/work-with-devin/ask-devin
  - DeepWiki MCP at https://mcp.deepwiki.com/mcp (no auth, public repos only). Three tools: `read_wiki_structure`, `read_wiki_contents`, `ask_question`. Private repos go through the Devin MCP with an API key. Docs give `claude mcp add -s user -t http deepwiki https://mcp.deepwiki.com/mcp`. https://docs.devin.ai/work-with-devin/deepwiki-mcp.md
  - Repos must be indexed for Ask/DeepWiki; environment repos are indexed automatically, others via Settings > DeepWiki. https://docs.devin.ai/work-with-devin/ask-devin
- Internals: Cognition publishes none. Open-source clone deepwiki-open (AsyncFuncAI): clone, embed, RAG "Ask", DeepResearch, LLM-generated docs and Mermaid diagrams, Python backend plus Next.js (secondary sources only). [documented by third parties] https://github.com/AsyncFuncAI/deepwiki-open (via search results; unverified)
- No published evidence on how wiki quality or staleness affects task success. [inferred: absent]

Minimal Claude-Code-native equivalent [inferred]:
- A `wiki/` (or `docs/wiki/`) tree of markdown, with an index page and a `wiki.json`-like page plan (title, purpose, notes) committed. Steering by purpose-per-page is the cheap, valuable part of Devin's design.
- Generation: a skill that runs a read-only `Explore`/haiku subagent per page using the page plan, and writes the page with file:line source links. No embeddings needed; Claude Code already searches with grep/glob.
- Freshness: a Stop or PostToolUse hook, or a CI/pre-push check, that maps changed paths to wiki pages (each page lists the paths it covers) and marks them stale or regenerates only those. Devin documents none of this, so this is where we could beat it cheaply.
- Consumption: CLAUDE.md points at `wiki/index.md`; the agent reads pages on demand. No MCP needed for own repos. DeepWiki MCP is only useful for third-party public repos.

## 2. Memory / Knowledge

Memory (current product) [documented] https://docs.devin.ai/product-guides/memory
- Stored: preferences, corrections with the rule, decisions and reasons, gotchas about repos/environment. Explicitly NOT stored: session summaries, task state (PR numbers), anything cheap to rediscover, secrets.
- Format: a "memory drive" = persistent git repo of markdown. `MEMORY.md` holds general preferences plus an index; other notes in folders (`my-app/`, `tools/`). One-line bullets with `[source: <session link>; added: <date>]`.
- Writer: Devin itself, during sessions (on correction, stated preference, reusable discovery). "Dreaming": a background session roughly daily (if user active) that merges overlapping notes, removes transient and stale unused notes, adds missed lessons, reorganises the index; preserves source links and explicit preferences.
- Validation: no formal validation step documented. Closest mechanisms: source link on every entry; Dreaming drops notes no session used; stale writes rejected and retried; conflicts resolved not overwritten.
- Scope: personal to the user within an org; not shared with teammates. New memories apply to future sessions only. Automation-started sessions neither read nor write memory. No repo-level memory.
- Retrieval: each session checks out the drive; `MEMORY.md` is loaded into context; other notes are searched and read only when the task needs them.
- Edit/remove: read-only in the UI; ask Devin in-session to forget; "Updated memory" card per session; toggles per user, org, enterprise (default on). No numeric limits stated.
- Open spec "Agent Memory Repo" (MIT): https://github.com/AgentMemoryRepo/agentmemoryrepo . Folder of notes; `MEMORY.md` root entry loaded every session and kept short; one-line bullets, optional `[key: value; ...]` metadata (recommended `source`, `added`); `[[path]]` links from memory root; agents update with no human in loop and push after every edit; one fact in one place, link elsewhere; git rejects a second push on the same line and the loser re-reads both versions; multiple memory repos can be loaded, agent asks when destination is unclear. Installable skill (`npx skills add AgentMemoryRepo/agentmemoryrepo --skill agent-memory-repo`) but NO hooks, scheduled jobs or startup scripts: dreaming and auto-load are Devin product features. [documented; full SPEC.md not read, secondary: https://rywalker.com/research/agent-memory-repo]
- Knowledge (older): trigger-described items, pinnable to all repos or one repo, auto-generated from README/structure and pulled from `.rules`, `.cursorrules`, `CLAUDE.md`, `AGENTS.md`; shows "Accessed Knowledge" per session. Now DEPRECATED, auto-migrating to Skills in Plugins. [documented] https://docs.devin.ai/onboard-devin/knowledge-onboarding.md
- Skills: SKILL.md with frontmatter (name, description, allowed-tools, argument-hint, triggers); read from `.agents/skills/`, `.devin/`, `.github/`, `.claude/`, `.cognition/`, `.windsurf/`; repo scope, or plugin scope at personal/org/enterprise; Devin SUGGESTS skills (with a Create PR button) after testing your app or learning setup; one active at a time. [documented] https://docs.devin.ai/product-guides/skills
- Lesson loop via Session Insights: L/XL sessions are auto-analysed at teardown; output has issue timeline, improved prompt, action items for setup/repo config, and "Knowledge Usage: useful vs misleading". Recommended follow-up is manual: delete or tighten misleading items, add skills for repeated issues. [documented] https://docs.devin.ai/product-guides/session-insights.md

Versus native Claude Code [inferred, plus documented Devin facts]:
- Same in kind: markdown memory index loaded at start, topic files read on demand (Claude auto memory MEMORY.md + topic files; CLAUDE.md; `.claude/rules`). Our own memory module is modelled on this spec (per your prior note).
- Devin adds: (a) memory as its own git repo with per-entry provenance (`source` session link, `added` date); (b) scheduled dreaming consolidation; (c) conflict handling via git; (d) skill suggestions as PRs; (e) per-session insights flagging misleading knowledge; (f) org/enterprise admin switches.
- Devin does NOT add (per docs): validation of a lesson before it is trusted, repo-scoped memory, or shared team memory. Its only quality controls are provenance, pruning of unused notes, and human review of skill PRs.
- Native replicas: provenance = a line format in a rules/memory file; dreaming = `/schedule` routine or a headless `claude -p` run over the memory dir; conflicts = git; "accessed knowledge" = a PostToolUse/InstructionsLoaded hook logging which files were read (feeds the used/misleading signal). ## 3. Playbooks and decomposition

- Playbook sections [documented] https://docs.devin.ai/product-guides/creating-playbooks.md : Procedure (ordered imperative steps, one per line, MECE), Specifications (postconditions: what must be true at the end), Advice and Pointers, Forbidden Actions, What's Needed From User; optional Overview. Org/enterprise scope, `!macro` names, versioned saves, iterate by running 2+ Devins in parallel on the same playbook and editing after you unblock them. Skills are the repo-versioned equivalent; playbooks are org-wide prompt templates. https://docs.devin.ai/product-guides/skills
- Planning before work [documented]: Ask Devin Plan mode scopes and breaks down the task, then hands a context-rich prompt to an agent session. No dedicated "Advanced mode" page exists in the index (llms.txt). https://docs.devin.ai/work-with-devin/ask-devin
- Parallel children [documented] https://docs.devin.ai/work-with-devin/advanced-capabilities.md : a coordinator session decides to split, groups files into work packages "that won't conflict", launches child sessions (own VM) each with prompt, playbook, tags, ACU limit; is woken when a child finishes or needs input; can message, sleep or kill children; auto-approve of child sessions is a setting. Not documented: concurrency limits, how results merge, dependency handling beyond "keep packages independent".
- Dynamic Workflows [documented] https://docs.devin.ai/work-with-devin/dynamic-workflows.md : a deterministic Python script calls `agent(prompt, phase, schema)` (JSON-schema structured result), `pipeline(items, stages...)`, `parallel([...])`, `log`. Fit: >=5 independent units plus a combine step, or staged audit -> fix -> verify; not for codemod-able work. Separate-VM agents pass work via git branches named in structured output. Shared-VM agents need non-overlapping files. Verify loops run until a check passes or progress stalls. Resumable by run ID with recorded results replayed, up to 7 days; editing a prompt reruns it and everything downstream. Cost: each agent is a full session. A good workflow can be saved as a skill (`workflow.py` + `SKILL.md`).
- No Devin concept of "intents" or test plans as first-class objects was found. The nearest: playbook Specifications (postconditions), schema'd agent outputs, and verify stages. [inferred]

## 4. Thin versus heavy

Cognition's own stance [documented]:
- 2025: default to a single-threaded linear agent; share full traces; "actions carry implicit decisions, and conflicting decisions carry bad results"; use a compression model for very long tasks. https://cognition.com/blog/dont-build-multi-agents
- 2026 update: multi-agent works "best today when writes stay single-threaded"; read-only helpers (search) are the common safe pattern; Devin plus a clean-context Devin Review loop; "smart friend" escalation sharing forked context; manager/child "map-reduce-and-manage" is preferred shape. Pitfalls: managers over-prescribe, agents wrongly assume shared state with children, children don't report upward by default, arbitrary agent networks are a distraction. https://cognition.com/blog/multi-agents-working

Thin (copy) [inferred from the above]:
- Markdown-in-git memory with a short loaded index, one-line entries with source+date, `[[links]]`.
- Postcondition-style playbooks/skills (Procedure, Specifications, Forbidden, Needs-from-user).
- Steered wiki page plan (purpose per page, capped notes).
- Clean-context reviewer on the final diff; read-only subagents; single writer.
- Post-session analysis producing "improved prompt / action items / misleading knowledge".
- Decomposition into file-disjoint work packages, structured (schema'd) child results, git branches as the handoff.

Heavy (do not copy):
- Per-child VMs, ACU metering/limits, managed fleet and wake-up plumbing, resumable 7-day workflow engine, hosted index for all repos, embeddings/RAG over code, enterprise admin matrix, DeepWiki hosting at 50k-repo scale, Devin Review as a bot with CWE tagging.

## 5. Evidence of lift or cost

- Devin Review: avg ~2 bugs per PR, ~58% severe; reviewer works better with no shared context ("clean context leads to a notable improvement ... generator-verifier loop"). No methodology. https://cognition.com/blog/multi-agents-working
- DeepWiki costs: Medium ~5-10 ACUs, High ~20-40 ACUs per wiki. https://docs.devin.ai/work-with-devin/deepwiki
- Review size bands: XS <=2.25 ACUs ... XL >18 ACUs; per-PR limit configurable. https://docs.devin.ai/work-with-devin/devin-review.md
- Dynamic workflows: "a run can use far more ACUs than a single session"; test on a small slice. https://docs.devin.ai/work-with-devin/dynamic-workflows.md
- Memory/dreaming/DeepWiki: NO published ablation, hit rate or task-success lift found in docs or the blog pages fetched. The only third-party coverage found is promotional (alphasignal, memorylake, explainx) and not evidence. [documented absence]
- Gaps: SPEC.md of Agent Memory Repo and the Cognition memory announcement post were not read; Cognition's DeepWiki generation internals are unpublished.

## Implications for rig [inferred]
1. Wiki: page plan with purposes + per-page covered-paths + hook-based staleness; generated by read-only haiku agents. Skip embeddings and MCP.
2. Memory: adopt the spec format; add what Devin lacks: a validation gate (lesson must cite evidence, e.g. a failing check it fixed) and a usage log to prune misleading entries.
3. Decomposition: file-disjoint packages, one writer at a time or worktree-per-package with branch handoff, structured results, one clean-context review at the end (matches CLAUDE.md here).
