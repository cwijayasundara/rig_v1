## 1. What a harness is (A1)

- Definition [quoted]: "everything in an AI agent except the model itself"; narrowed to the coding-agent user's outer harness built "for our use case and system". Built-in harness (system prompt, retrieval, orchestration) sits between model and user harness.
- "Engineering a user harness for a coding agent is a specific form of context engineering." [quoted]
- "The agent harness acts like a cybernetic governor, combining feed-forward and feedback to regulate the codebase towards its desired state." [quoted]
- Guides = feedforward: "anticipate the agent's behaviour and aim to steer it before it acts." Sensors = feedback: "observe after the agent acts and help it self-correct." [quoted]
- Need both: feedback-only agent "keeps repeating the same mistakes"; feedforward-only never learns "whether they worked". [quoted]
- Computational: "deterministic and fast, run by the CPU" (tests, linters, type checkers, structural analysis); "cheap and fast enough to run on every change, alongside the agent". Inferential: AI code review, "LLM as judge"; "Slower and more expensive; results are more non-deterministic." [quoted]
- Inner vs outer loop: A1/A2 do not use the words as such. They use lifecycle position (see cadences). A3 uses them: inner = agent invokes harness during development; outer = evaluator runs the 178 checks once, independently. [quoted/paraphrased]
- Regulation categories [quoted]: maintainability (easiest), architecture fitness (fitness functions), behaviour (hardest; "puts a lot of faith into the AI-generated tests, that's not good enough yet").

### Steering loop
- "steer the agent by iterating on the harness." "Whenever an issue happens multiple times, the feedforward and feedback controls should be improved" so it becomes less likely or is prevented. [quoted] It is a human-run loop: observe a recurring failure, then add or tighten a guide or sensor. Framed as "an ongoing engineering practice, not a one-time configuration" (per prior notes; I did not re-verify this exact line).

### Cadences (A1, A2)
- A1 "Keep quality left": checks "as far left in the path to production as possible"; "the earlier you find issues, the cheaper they are to fix." Before integration: linters, fast tests. Post-integration: mutation testing, broader reviews. Continuous: drift sensors (dead code, dependency scanners). Inferential checks: "Not on every commit." [quoted]
- A2 three tiers [per extraction]: sensors that run continuously alongside the agent in-session; the same computational ones again in CI; slower-cadence sensors for accumulating drift.

## 2. The cost article (A3)

Setup [quoted unless noted]
- Task: backend-for-frontend (Java, Spring Boot, Maven) for product discovery: 4 operations (GET /health, POST /products, GET /monitor/{id}, GET /findAvailableProducts), calls an Order API, publishes the first product to Kafka `product-queries`, with retries/idempotency, 429/502/503 rules.
- Conditions: harnessed vs unharnessed, 10 paired runs per model, Codex, low reasoning effort, isolated Docker per attempt. Acceptance = app starts and passes all 178 external acceptance tests the harness never saw.
- Models: GPT-6 Sol (frontier) and GPT-6 Luna (cost-optimised). Exploratory only: "In exploratory runs with Claude Sonnet 4.6, Claude Opus 4.6, and Gemini 3.8 Flash" each "managed to complete the task unassisted on the first try"; no numbers. Haiku never tested.
- Harness (Specmatic): guides = OpenAPI + AsyncAPI specs, request/response examples, an API-development skill. Sensors = contract conformance, API tests, CTRF reports, API coverage reports. (Prior notes add example validation, contract-driven mocks, timing helpers; plausible, not re-verified.)

Numbers (10-run averages)

| Model | Harness | Tokens | Time | Est. cost | Accepted |
|---|---|---|---|---|---|
| Sol | yes | 11,331,970 | 19m53 | ~$2.679 | 10/10 |
| Sol | no | 1,076,371 | 6m51 | ~$0.406 | 10/10 |
| Luna | yes | 22,933,648 | 35m | ~$0.273 | 10/10 |
| Luna | no | 5,860,736 | 15m56 | ~$0.086 | 3/10 |

- Sol: harness = ~10.5x tokens, ~3x time, ~7x cost, same result. Luna: +17.07M tokens, +19m04, +$0.187 per attempt, ~3.9x tokens; 3/10 to 10/10.
- Harnessed Luna ($0.273) cost ~33% less than unharnessed Sol ($0.406). But "the harness did not unlock a capability Luna lacked"; it "turned a 3-in-10 baseline into 10-for-10 reliability."
- Unharnessed Luna passed 94.8% of functional checks on average (near misses, not broken apps).
- Unharnessed failures: deferred creation at timeout returning 503/400/429 instead of 202 (7 runs); missing monitor links (7); Kafka contract violations (3: stray `__TypeId__` header, `"categories": null`); 415 vs 400; env var name mismatch. [quoted/paraphrased] Common thread [inferred]: exact, enumerable requirements from the brief that the agent dropped.

Caveats the author states [quoted]
- Costs are API-equivalent estimates. "They exclude the upfront effort of authoring, reviewing, and maintaining the contracts, examples, assertions, and harness" (and diagnosing/repairing failures).
- One greenfield Java service, one detailed brief (author does not know the effect of a vaguer one), low reasoning effort only. "it cannot establish long-run reliability." Guides and sensors added together, so "cannot isolate their individual contributions."
- The loop was not automatic: "The feedback loop depended on the agent invoking these tools during development; it did not run automatically after every code edit."

When sensors should run, by model strength [quoted]
- "What changes with model capability is not whether independent sensors are needed, but when they run."
- Cost-optimised: "When a cost-optimized model produces inconsistent results, run a behavioral harness throughout development" ("executable attention").
- Frontier: "run the automated tests once as a deterministic final verification gate before acceptance." A "final gate only" variant (sensors "available to the agent only at a final verification gate") is proposed, NOT tested.
- Interpretation, labelled as such by the author: harness as "external memory and attention aid"; "A requirement can be explicit in the brief and still lose influence during implementation." Also "The checks can enforce only the expectations humans encode."
- Also "My original assumption was too blunt. A behavioral harness is not an automatic win for every model on every task." [per extraction/prior notes]

What it does NOT show [inferred]: nothing about thin vs full harness (only a full one tested); nothing about Claude models quantitatively; no setup-cost; no legacy code; the 178 tests are the same kind of artefact as the sensors (contract/examples), so the harness partly "teaches to the test" in spirit, though the answer key was hidden.

### Warnings collected [quoted]
- "I worry about feedback overload for the agent, sending it into a spiral of over-engineered refactorings."
- Acceptance tests raise coverage but are light on assertions: "false sense of security in test effectiveness."
- Sensors "are not a magical solution to take the human totally out of the loop." Human review of all generated tests is "unrealistic."
- "What I haven't seen ... but suspect can become more of an issue, is conflicts between sensors."
- Sensors cannot catch "Misdiagnosis of issues, overengineering and unnecessary features, misunderstood instructions"; "Correctness is outside any sensor's remit if the human didn't clearly specify what they wanted" (A1).
- Silent sensors: "If sensors never fire, is that a sign of high quality or inadequate detection mechanisms?" (A1)
- Getting agents to RUN sensors: AGENTS.md instruction is "quite unreliable" ("many, many times why it had not run the sensors check"); options listed: hook after every file edit ("probably a good starting point"), git pre-commit hook ("force a sensors check ... before code even gets into a commit"), custom tool/extension.

## 4. Human role, maintenance, deleting, fit

- Human role [quoted]: not to eliminate input, but "direct it to where our input is most important"; agents lack social accountability, organisational memory, and a sense of which conventions are load-bearing (A1, per extraction). Review starting point: "the exceptions AI created (suppressed warnings, increased thresholds)" (A2). Humans own the spec: checks "enforce only the expectations humans encode" (A3).
- Maintenance: harness is "expensive" to build so "prioritise" (A1); A3 excludes authoring/maintenance cost from its numbers. Coherence open question: "How do we keep a harness coherent as it grows, with guides and sensors in sync, not contradicting each other?" Also "We need a way to evaluate harness coverage and quality similar to what code coverage and mutation testing do for tests."
- Sensor history (A2): author logged sensor states each check to see whether failures decline, which sensors never fail (maybe unnecessary), which rules fail often (guides need improvement). [quoted/paraphrased] This is the only pruning mechanism offered.
- Deleting guides: NOT addressed beyond a question: "Once we feel confident in a set of sensors, what guides can we delete?" Also "Do sensors make the use of weaker models more realistic?" (A2). No procedure, no data.
- Fit: "Harnessability": typing, clear module boundaries, frameworks afford controls ("Without those properties, those controls aren't available to build"). "the harness is most needed where it is hardest to build" (legacy). Ambient affordances = "structural properties of the environment itself that make it legible, navigable, and tractable to agents".
- Topologies/templates: bundles of guides+sensors per service topology; "a few common topologies of services that cover 80% of what they need" (informal); "Teams may start picking tech stacks and structures partly based on what harnesses are already available"; Ashby's Law (regulator needs as much variety as the system); "committing to a topology narrows that space". Templates "would face the same versioning and contribution problems" and instances "start fall out of sync with upstream improvements." [quoted]

## 6. For a thin, Claude-Code-native harness

Copy [inferred from quotes above]
1. Put the contract in machine-checkable form (acceptance tests/examples derived from the brief) and run it independently of the agent's own tests. A3's failures were exact, enumerable brief requirements; a checker that restates them is "executable attention".
2. Tier by cost: cheap deterministic checks (types, lint, relevant tests, secrets) on every edit/commit; expensive ones (mutation, inferential review) post-integration/manual; "Not on every commit" for LLM review.
3. Make execution mechanical, not advisory: Claude Code hooks (post-edit, pre-commit/Stop) instead of AGENTS.md pleas (A2: unreliable). A3 also notes the loop did not auto-run, so forcing it matters.
4. Cadence by model strength: stronger model (Opus/Sonnet) = one final independent gate; weaker (Haiku) = continuous. Treat as hypothesis: A3 did not test "final gate only", nor Claude tiers.
5. Steering loop: add a guide/sensor only when a failure recurs ("multiple times"); log sensor results; periodically prune sensors that never fire and guides covered by a sensor (the pruning idea is A2's, unproven).
6. Custom, actionable sensor messages (lint messages as prompt injection); keep large outputs out of context (query_stryker.py idea).
7. Human review aimed at agent-created exceptions (suppressions, raised thresholds) and at the spec.
8. Prefer sensors in the tool you already have; "keep the tool itself simpler", push customisation to users (A2).

Do NOT copy
- The full Specmatic-style harness as default: on the strong model it cost ~7x for no acceptance gain; A3's numbers exclude authoring cost. [quoted numbers; recommendation inferred]
- Many sensors with no cap: feedback overload/conflicts are flagged risks; no source gives a count limit.
- Reliance on AI-generated tests or coverage as proof of behaviour.
- Templates/topology bundles for now: Fowler himself flags versioning/drift; heavy for a thin tool.
- Treating A3 as Claude evidence: Claude only appeared in unquantified exploratory runs; GPT-6 models, Java, one task, low reasoning effort, n=10.
- Expecting sensors to cover misdiagnosis, overengineering or vague requirements: out of remit; the spec/brief quality is the human's job.
