## 1.2 Promotion ladder in `learn`

Today `learn mine` finds a finding or waiver that recurs in 2 changes (the proposal's "twice"), `learn replay` gates a regex rule, and a person applies
the result. Missing: it never says which fix is the strongest one that fits, nothing enforces that a promotion carries passing replay evidence, and an
exception (a waiver) has no end date.

- **Ladder.** `learn mine` prints, for each candidate, the highest feasible rung and the exact mechanism, from a fixed table keyed on the review category or waiver sensor:
  architecture (`coupling`, `responsibility`, `abstraction` -> a layer edge in architecture.md, `/rig:arch`); count ratchet (`duplication`, `size` -> a `ratchet` sensor); test or
  contract (`tests`, `contract`, `data` -> a test, a frozen example); rule (a pattern over added lines -> `.rig/rules.json`); lesson (everything else -> one line of `lessons.md`). **[my call]** the table lives in `learnmine.ts` as data.
- **Evidence is mandatory.** `learn replay` writes `.rig/learn/replay-<id>.json` (the rule's hash, the earning slugs, pass or fail). New `learn proposal` reads `.rig/learn/proposal.md` and rejects any `PROMOTE` or `LAYER` line with no
  passing replay file whose hash matches what the line proposes. `LAYER` is new: `learn replay --layers <block.md> --earned a,b` runs the layering sensor derived from a `rig-layers` block over each earning change's diff and passes only when it fires on every one and on no other shipped change.
- **Exceptions end.** `waive` records `expires` (default 30 days, `--days N`, at most 180) and an expired waiver stops applying, so the finding comes back. **[my call]** A row with no `expires` (written before this) never expires, and `sensors` shows "no expiry". The approver is the existing `by`.
- Not measured: whether proposals promoted this way reduce repeated findings (needs shipped history; the loop's own eval, `npm run eval:learn`, is the place).

## 1.3 Scope check

- A charted intent (`.rig/product/intents/<slug>.md`, frozen by the chart approval, so a PR cannot widen it) may carry frontmatter `scope: [glob, ...]` and `touches: [glob, ...]` (cross-slice work, named on purpose). `templates/intent-format.md` documents both; both optional.
- New built-in sensor `scope` (deterministic, no model): for a change whose product intent has `scope`, every changed file must match `scope`, `touches`, the change's own `.rig/changes/<slug>/**` folder, or the intent's test globs. **[my call]** A finding names the file and the intent line; **warn at Stop, block at ship and CI**, waivable by a person like any sensor. A change with no product intent or no `scope` is not checked (said in `status`).
- Not built, as the proposal says: a scaffolded directory convention. Not measured: scope-creep rate (needs an eval task that tempts it).

## 1.4 Golden slice per stack pack

- `templates/slices/<stack>/`: a small exemplar feature in the stack's own idiom and layout, four layers by directory (domain, app, infra, http), with tests, plus `slice.json` (the source globs and the `rig-layers` block for it).
  **[my call] node and python first**, the two I can run here; the mechanism is data, so another stack is a directory.
- `sdlc.ts slice gen`: writes `.claude/rules/rig-slice.md` with `paths:` frontmatter (native Claude Code rules, loaded only when the model works on matching files) that states the conventions and points at the exemplar, and merges the slice's layers block into `architecture.md` for a person to approve (`/rig:arch`), never enforcing it unapproved.
- `sdlc.ts slice scaffold <name>`: generates a new feature slice from the exemplar with the name substituted, under the repo's own layers. **[my call]** it never overwrites a file.
- Not measured: whether an exemplar raises conformance or acceptance (the proposal's eval arm: with and without the exemplar, scored by `layerViolations`; it costs a live run and is not run here).
