# Intent map: formal, empirical, and not promised

Date: 2026-11-07. Status: design, with a runnable acceptance oracle. The harness does not enforce this yet. Nothing in `scripts/`, `skills/`, or `templates/` changed.

Source: the recommendation after reading [PDD Kit](https://githubnext.com/projects/pdd-kit/) and the [Microsoft Research post](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/). PDD Kit itself is not a dependency. It has no public installer, and it only checks Rust with Verus. This design takes the review shift those pages describe and puts it on the Python work rig already runs.

## Why

rig already freezes a plan. `/rig:approve` hashes `spec.md`, `plan.md`, and the contract files, and `harness-tamper` blocks a later edit. `red-proof` demands that new tests fail on the base. `test-tamper` blocks a weakened test. `contracts.run` fails the build when a frozen suite fails. Scripts decide.

What stays open is the behaviour claim. A numbered behaviour becomes a few tests. Those tests can pass for a function that is wrong on the next input. The login sentence "you only get a token with the right password" is true of a login that refuses everyone. On the tasks measured through 2026-10-31, rig and a bare model both passed, and rig cost about three times as much. Another shop-task eval will repeat that.

The two articles answer that hole with one document a person reviews. Each requirement is formal (a checker, every input in the model), empirical (a scenario run and recorded, labelled evidence), or not promised. The pull request is a receipt printed from that document. A clause that rules nothing out is caught by planting one bug per clause. A test that only repeats a proved clause is dropped.

## Goals

1. One file, `intent-map.md`, is the contract for a change that opts in. A person approves it before any implementation body exists.
2. Every said sentence is a row of kind `formal`, `empirical`, or `not-promised`. A sentence with no row fails the check.
3. A formal row names clauses. At ship, the implementation meets them, and one planted bug per clause is rejected.
4. An empirical row names Given/When/Then scenarios written at plan time, while their status is `planned`. The script records the command, the result, and the commit. The agent does not.
5. The PR body receipt is that table, generated by the script.
6. A change with no `intent-map.md` keeps today's path. Existing evals and the journey do not start failing.

## Non-goals

- Verus, Rust, Chopin, decision-card chrome, the quiz, reviewer agents, and generated pictures. The grill can still ask the both-ways question. The durable record is the decision id on the row.
- A second prose spec beside the map. When the map exists, `spec.md` `## Behaviours` is a projection of the rows, not a second place to edit.
- Proving bcrypt, the database, the clock, the signer, the UI, or that a call finishes. Those are empirical rows or `not-promised` rows.
- A live paired eval in this change. The deterministic oracle below is the regression test. The lift arm is specified and not built.

## Anti-goals

- A green formal check on a one-directional reading of a both-ways decision. "Only when" and "always" are different clauses, and the row has to name both.
- An empirical `pass` written into the map by the agent, or written before ship.
- Moving a formal row to `not-promised` without a new approval. The map is a frozen contract file, so `harness-tamper` already treats that edit as a block until a person re-approves.
- Calling an empirical pass a proof. The receipt says `evidence, not proof`.
- A missing checker counting as a pass. If the formal command cannot run, ship fails closed.

## Reason for new code

GOAL rule 2, second bullet. The verdict has to be deterministic and outside the model. Claude Code has no native check that a behaviour holds for every modelled input, that each clause rejects a mutant, or that a scenario's result was recorded by a script. Approval, staleness, and `harness-tamper` stay as they are.

## The file

Normative example: `eval/fixtures/intent-map/login/intent-plan.md` (approve time) and `intent.md` (ship time). A change stores the same text at `.rig/changes/<slug>/intent-map.md`. It is not `intent.md`. That name is already the change's intent.

Sections, in order:

| Section | What a row holds |
|---|---|
| Said | `S1`, `S2`, … the person's words, one sentence each |
| Decisions | `D1`, … the chosen reading. A both-ways decision starts with `both-ways` |
| Map | One row: `said`, `decision`, `kind`, and `clauses` or `scenarios` |
| Formal | `C2 only-when`, `C3 always`, or a clause with no direction. The English sentence is the line under the heading |
| Empirical | `E1` with `given`, `when`, `then`, and `status` |
| Not promised | `N1`: the sentence nobody is promising |

Kinds are `formal`, `empirical`, and `not-promised`. A formal row names clause ids. An empirical row names scenario ids. A not-promised row's id appears in Not promised and names no clause.

At plan time every empirical `status` is `planned`, with no `command` and no `commit`. At ship time `status` is `pass`, and `command` and `commit` are present. Those three result fields are written by the script from the process it ran.

`spec.md` `## Behaviours`, when a map exists, lists the same ids and the same words. `/rig:plan` writes that section from the map. A hand edit that drifts is a block. Traceability then looks for those ids in tests only for empirical rows. A formal row is traced to its clause, not to a unit test.

## Checks

`eval/intent-map.mjs` is the oracle. `scripts/intentmap.ts`, when built, must return the same rule ids. The rules:

| Rule | When it fires |
|---|---|
| `unmapped-said` | A Said id is on no row |
| `unknown-kind` | A row's kind is not one of the three |
| `missing-clause` | A formal row names no clause, or names one with no Formal section |
| `orphan-clause` | A Formal clause is on no row |
| `both-ways` | The row's decision is both-ways, and its clauses lack `only-when` or lack `always` |
| `missing-scenario` | An empirical row names no scenario, or names one with no Empirical section |
| `empirical-early` | Plan time, and a scenario status is not `planned` |
| `empirical-open` | Ship time, and a scenario is still `planned` |
| `empirical-unrecorded` | Ship time, status `pass`, and the command or the commit is missing |
| `stale-scenario` | The hash of `given` / `when` / `then` differs from the hash stored at approval |
| `missing-not-promised` | A not-promised row is absent from Not promised |
| `formal-failed` | Ship time, and the implementation breaks the clause |
| `unmutated` | Ship time, and a formal clause has no planted bug |
| `vacuous` | The planted bug still satisfies the clause |
| `prune` | A test file names a formal clause id and no empirical scenario id |

Approval hashes `intent-map.md` and a `freeze.json` of the scenario hashes (`scenarioHash` in the oracle). It does not hash the implementation. A later edit of the map or of a scenario's given/when/then goes stale, which is today's `frozenFindings` once the map is listed in `contracts.files`.

The receipt is `receipt()` in the oracle. Formal lines say `holds` or `fails`. Empirical lines say `evidence @ <commit>` and end with `(evidence, not proof)`. Not-promised lines quote the sentence. `scripts/prbody.ts` appends that block. It does not ask a model to summarise it.

## The login oracle

`eval/fixtures/intent-map/login/model.py` is the formal column for this one function. The grid is the 84 worlds the words allow: identity `neither | email | username | both`, the row that identity's mathematical lookup would return, password `right | wrong | unreadable`, lookup failed or not, signing failed or not. Email wins inside that mathematical lookup, so the grid never pairs an email with an admin row. An implementation may still search the wrong table. The clauses call the mathematical lookup, not the implementation's table.

| Clause | Direction | What it holds |
|---|---|---|
| C2 | only-when | A token implies the right password for the named account, that account's id, and the role of the table the words selected |
| C3 | always | The right password for a named account gets a token, or a 500 when lookup or signing failed |
| C7 | | An admin role implies the identity was username only |
| C8 | | An email login's token carries the customer role |
| C9 | | An email, when sent, selects the customer table |

The good implementation is `lookup_target` plus `decide`. The planted bugs, in `mutants.json`:

| Bug | Clause that must reject it |
|---|---|
| `wrong_password_tokens` | C2 |
| `refuse_everyone` | C3 |
| `email_loses` searched as username-before-email | C7 |
| `always_admin_role` | C8 |
| `email_loses` | C9 |

`check_password` stays empirical (`E1`, `E2`), status `planned` in `intent-plan.md` and recorded against commit `8b8b70f` in `intent.md`. "Login finishes" is `N1`.

This grid is finite, so the oracle enumerates it in Python and does not need CrossHair. A property that is not a finite grid uses a formal command, recorded like any other sensor. **(guess: the command is `crosshair check`, cadence `ci`, blocks, and only on changes that have a map.)** If that command is not installed, ship of a formal row fails closed. The row is not relabelled empirical to get around it.

## Where the wiring goes

Not built. The next change, after this design is approved, is the one that makes a real repo fail these checks.

| Piece | Change |
|---|---|
| `scripts/intentmap.ts` | Port `parse`, `check`, `receipt`, and `scenarioHash`. Same rule ids |
| `scripts/intentmap.spec.ts` | The cases in `eval/intent-map.test.mjs`, against the port |
| `scripts/verify.ts` | Plan phase at approve time. Ship phase inside verify. Findings use the rule id as the sensor id |
| `scripts/prbody.ts` | Append `receipt()` |
| `scripts/registry.ts` | Reserve the new sensor id. Do not add a built-in that runs on repos with no map |
| `skills/plan/SKILL.md` | Write `intent-map.md` from the grill, project `## Behaviours` from it, leave empirical status `planned`, leave formal bodies empty |
| `skills/build/SKILL.md` | Bodies only after approval. The script fills empirical result lines after the command exits. Plant the mutants in a scratch copy, never on the branch |
| `skills/approve/SKILL.md` | Hash the map and `freeze.json`. Refuse while plan-phase findings exist |
| Python stack pack | The formal command, absent until a map exists |

A map is opt-in. `check` returns no findings when the file is absent. **(guess.)** Forcing every change through a map would make a one-line fix pay for a proof, which fights the task-router design.

## How to test

The oracle is the means. From the rig repo:

```bash
node --test eval/intent-map.test.mjs
```

`npm test` also runs it, because `test:e2e:unit` includes `eval/*.test.mjs`. Python 3 is the only extra tool. CrossHair is not required.

| Test | What it holds |
|---|---|
| Plan-time login map | No findings while bodies are absent and both scenarios are `planned` |
| Ship-time login map | Good implementation, every mutant rejected on its clause, evidence recorded, receipt wording |
| `freeze.json` | Equals `scenarioHash` of the approved given/when/then |
| `cases/gap.md` | `unmapped-said` for the admin-token sentence |
| `cases/one-way.md` | `both-ways`, because D1 has only C2 |
| Status `pass` on the plan file | `empirical-early` |
| `freeze.json` with `E1` replaced | `stale-scenario` |
| Mutants that still satisfy their clauses | `vacuous` |
| `cases/prune.py` | `prune`, because the test names C2 and no `E` id |

Run on 2026-11-07: 5 tests, 5 passed, `node --test eval/intent-map.test.mjs`.

The lift arm is not this oracle. It is a later `eval/` task whose hidden checks are "refuse everyone fails" and "email loses fails", while the tests an agent is likely to write can pass for a login that refuses everyone. Keep the map only if that arm accepts more than the bare model at a cost that is still worth paying. Do not use the shop tasks from 2026-10-31. Those already pass bare.

## Decisions

1. **(my call)** The map is opt-in, per change, under `.rig/changes/<slug>/intent-map.md`.
2. **(my call)** The login oracle enumerates a finite grid. CrossHair is only the command for a property that grid cannot cover, and a missing command fails the ship.
3. **(my call)** `spec.md` behaviours are generated from the map when the map exists. They are not a second contract to approve.
4. **(my call)** Wiring into approve, verify, and the PR body waits until this design is approved. The oracle is the contract for that wiring.
