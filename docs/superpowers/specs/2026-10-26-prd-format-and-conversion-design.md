# A PRD format for coding agents, and converting any PRD into it

Date: 2026-10-26. Follows `2026-10-26-prd-fidelity-design.md` (the requirements ledger, merged in 2d1dd84).

## Relation to the PRD fidelity design

This design builds on [`2026-10-26-prd-fidelity-design.md`](2026-10-26-prd-fidelity-design.md) (merged in 2d1dd84) and
changes one part of it.

| Part of the fidelity design | Here |
|---|---|
| The requirements ledger, `sprint-<N>/requirements.md`, and its line format | kept; now **generated** by `S prd ledger` from the PRD's numbered criteria instead of written by the chart coordinator |
| Ledger ids `FR-4.2` / `G-n` | replaced for new charts by the PRD's own `AC-n.m`, `DR-n`, `NFR-n` |
| The "nothing left unquoted" check (`prdBlocks`, `unquoted`, `normalise`) | reused for the conversion map, over `source.md` |
| `rule-uncovered`, `rule-untested`, `unknown-id` | kept, over the generated ledger |
| The evaluator's `weakened` category | reused in its new conversion mode |
| The confirm pass, `approve chart-<N>` refusing open findings, `waive chart-<N>` | unchanged; `approve chart-<N>` also requires a current PRD approval for a converted sprint |
| The change's `requirements.md`, the PR reviewer reading it, ledger findings never deferred | unchanged |
| The PRD copy kept verbatim | the person's words are kept verbatim in `source.md`; `prd.md` is the converted, approved PRD |

## Why

The ledger stops a rule from being dropped between the PRD and the code, but it starts from whatever the person wrote. The
colleague's PRD (`docs/feedback/feedback_1.html`) stated "ids start at 1 and are never reused" as prose, where nothing numbered
it, so the chart could weaken it without any check noticing. A PRD written for a coding agent states every rule as its own
numbered, testable line. The sources agree on this:

- Atomic, testable criteria, each paired with an eval (Miessler's "Ideal State Criteria"); `WHEN <trigger> THE SYSTEM SHALL
  <response>` criteria (Kiro, EARS); success criteria with input/output examples (Osmani).
- Sections a person forgets: always/ask first/never boundaries, concrete examples and error shapes, exact stack versions,
  a dated decisions log (Osmani; Miessler's Decisions; the AI-native SDLC playbook's intent → spec → plan chain).
- A draft by the model from the person's material, reviewed and accepted by a person, never silently taken as the spec
  (the playbook: "The product owner reviews that spec, but doesn't write it"; Spec Kit: defaults first, few clarification
  markers).

Sources: addyosmani.com/blog/good-spec, claude.com/resources/articles/the-ai-native-sdlc-playbook,
danielmiessler.com/blog/writing-is-closer-to-thought-than-code, kiro.dev specs docs, the EARS notation.

## Goals

- One PRD template whose every rule is a numbered line a test can assert.
- Any PRD the person brings is converted into that template before `/rig:chart` decomposes it, losing nothing, and the
  original is kept untouched.
- A person approves the converted PRD before decomposition.
- The requirements ledger is generated by script from the (converted) PRD's numbered criteria; no model writes it.

## Non-goals

- Rejecting a PRD for its format. rig still accepts any PRD; it converts instead of refusing.
- Writing the PRD for the person from nothing. `/rig:init` points to the template; drafting a PRD from an interview is a
  later piece of work.
- Changing anything after the ledger: intents, test cases, the change's `requirements.md`, the PR review and the chart
  approval rules all stay as merged.

## Anti-goals

- A conversion that quietly rewrites the person's intent. Every sentence of the original is mapped to what it became, by
  script, and a reviewer looks for loosened rules before the person approves.
- A template so heavy that people stop using it. Prose stays welcome in Context, Goals and Scenarios; only the rule-bearing
  sections are strict.

## Decided (owner, 2026-10-26)

- rig provides a PRD template; a PRD not in it is converted into it before decomposition.
- A person approves the converted PRD before decomposition.
- The ledger is generated from the converted PRD's numbered criteria.

## The template (`templates/prd-format.md`, replaced)

Frontmatter `product`, `sprint`, `engineers`, `owner` as today. Sections, in order:

| Section | Holds | Strict? |
|---|---|---|
| Context and problem | who hurts and why | prose |
| Goals and success metrics | goal, metric, target | prose |
| Non-goals | what is not built | bullets |
| Users and scenarios | walk-throughs with real values (`S1. Adds "Coffee" x2 at 8.50; total 17.00`) | prose |
| Functional requirements | `### FR-n: <name>`, then `Need:`, `Priority:`, `Depends on:` lines and numbered criteria `- AC-n.m: ...` | strict |
| Data rules | invariants on stored data: `- DR-n: ...` (`DR-1: Each item id is an integer starting at 1.`) | strict |
| Non-functional requirements | `| NFR-n | category | requirement | target | verified by |`, target a number and unit | strict |
| Examples | fenced sample inputs, outputs and error shapes, each with a one-line caption naming the AC it shows | fenced |
| Boundaries | `Always:`, `Ask first:`, `Never:` bullets for the building agent | bullets |
| Integrations and constraints | stack with exact versions, external systems, hosting | bullets |
| Decisions | `- YYYY-MM-DD: <decision> — <why>` | bullets |
| Open questions | `none`, or one bullet each | bullets |

A criterion is one line, `- AC-n.m: WHEN <trigger> THE SYSTEM SHALL <response>` or `- AC-n.m: Given <state>, when <action>,
then <result>`, with exact values (numbers, statuses, error names, messages). Errors are criteria of the FR they belong to
(`AC-1.3: WHEN quantity is 0 THE SYSTEM SHALL raise ValidationError and leave the cart unchanged`). The template's comments
carry one worked FR, one DR and one example, taken from `docs/prds/shopping-cart-app-prd.md`.

## The format check (`S prd check <N> [--json]`, `scripts/prdformat.ts`)

Pure over text, like `chartcheck.ts`. Findings, all `block`:

- `prd-section`: a strict section is missing (Functional requirements always; Data rules, Non-functional requirements and
  Boundaries may hold `none`).
- `prd-criterion`: an FR with no `AC-n.m`; a criterion whose id does not match its FR; a criterion without the WHEN/SHALL or
  Given/when/then shape.
- `prd-prose`: a line under an FR (other than `Need:`, `Priority:`, `Depends on:`) or under Data rules that is not a
  numbered criterion: "a rule written as prose; make it an AC or a DR".
- `prd-id`: a duplicate AC, DR or NFR id.
- `prd-nfr`: an NFR row whose target has no number.

A PRD with no findings is "in format".

## `/rig:chart` step 1, rewritten

1. Find the PRD as today. Copy the person's file to `sprints/sprint-<N>/source.md` unchanged (when the given path is the
   sprint's own `prd.md`, move it to `source.md` first). Never edit `source.md`.
2. Run `S prd check`. **In format:** copy `source.md` to `prd.md` and go on to the gap pass; no conversion and no PRD
   approval are needed, because the person wrote it in this form.
3. **Not in format: convert.** The coordinator writes `prd.md` in the template from `source.md`, and
   `sprints/sprint-<N>/conversion.md`, the conversion map. It never invents a rule, a number or an answer: anything unclear
   goes under `## Open questions`. The gap pass's questions are asked here, in the same single batch, and their answers go
   into `prd.md` as criteria or Decisions marked `(answered at chart)`.
4. `S prd check <N>` then `S prd map <N>` (below); fix every finding, at most one round.
5. Launch `rig:evaluator` once in a new **conversion mode** with `source.md`, `prd.md` and `conversion.md`. It reports
   only `weakened` (a rule whose number, limit, start value, "never", "only", "every" or "unique" did not survive),
   `invented` (a criterion no source sentence supports) and `ledger` (a source sentence wrongly mapped to context). Write
   its reply to `sprints/sprint-<N>/conversion-review.md`. Fix its findings in one round; no second review.
6. Stop and tell the person: read `prd.md` (beside `source.md` and `conversion-review.md`), then run
   `/rig:approve prd-<N>`, then `/rig:chart <N>` again. Commit on `rig/chart-<N>` so the review happens on the branch.

On the re-run, chart sees `source.md`, a PRD approval that is current, and continues at the design step. With a stale or
missing PRD approval it repeats step 6 and stops.

## The conversion map (`conversion.md`) and `S prd map <N>`

One line per sentence, bullet, table row and fenced block of `source.md`:

```
- AC-4.1, DR-2 source.md:18 "Ids start at 1 and are never reused."
- context source.md:3 "Shoppers lose carts today." — motivation, kept in Context
```

`S prd map` reuses the ledger's quoting rules (`prdBlocks`, `unquoted`, `normalise`) with `source.md` as the text and every
section in scope:
- `map-unquoted`: source text no row quotes (a lone number or negation counts, as in the ledger);
- `map-misquote`: a quote not in `source.md`, or far from its line;
- `map-id`: a row naming an id `prd.md` does not define;
- `map-reason`: a context row with no reason;
- `map-fence`: a fenced block of `source.md` whose content does not appear in `prd.md` (examples are copied, never retyped).

## Approving the PRD

`/rig:approve prd-<N>` (human only, `SDLC_HUMAN`, `ownerOrFail`) records `sprints/sprint-<N>/prd-approval.json` with who,
when and a hash of `prd.md`, `source.md` and `conversion.md`. It refuses while `prd check` or `prd map` has a finding, while
`prd.md` has an open question, or while `conversion-review.md` has a finding not marked fixed. The file is denied to the
model in `templates/settings.json` and `templates/managed-settings.json` and listed as a human row in CI, like the chart
approval. `approveChart` refuses a converted sprint (one with `source.md` and `conversion.md`) whose PRD approval is missing
or stale. `/rig:approve` with no argument names `prd-<N>` when that is the pending gate. The journey shows the gate.

## The generated ledger

`S prd ledger <N>` writes `sprints/sprint-<N>/requirements.md` from `prd.md`: one `rule` row per AC, DR and NFR (an
`(answered at chart)` criterion is an `answer` row), its quote the criterion text, its line the line in `prd.md`. The ledger
line format stays, so everything downstream reads it unchanged. Ids are the PRD's own (`AC-4.1`, `DR-2`, `NFR-1`); the
`FR-4.2`/`G-n` scheme is no longer produced. `RULE_ID`, coverage and `changeRequirements` accept `DR-n` and a ledger row
named by an `NFR-n` id. Chart runs `S prd ledger` after the gap pass and again whenever `prd.md` changes. `chart check`
reports `ledger-stale` (block) when `requirements.md` differs from what `S prd ledger` would write; the old `ledger-unquoted`
check stays and must pass trivially on a generated ledger.

## How intents cite the new ids

Behaviours already cite an FR plus a criterion, `- B2 (FR-4, AC-4.1): ...`; that stays the form. A data rule is cited the
same way by the behaviour that enforces it, `- B3 (FR-4, DR-2): ...` (an FR is still required, so `intent-untraced` is
unchanged), and an NFR row by its own id, as today. The parent FR of a generated row is derived from its id (`AC-4.1` belongs to `FR-4`), not written in the alias slot: an
alias would let a behaviour citing only `FR-4` cover every criterion of FR-4. `changeRequirements` selects by the intent's
`prd:` FR ids: an AC row comes with its FR, an NFR row with its NFR id, and a DR row only when a behaviour of the intent
cites it. A criterion marked `(out of scope: <when>, decided by <who> — <reason>)` becomes an out-of-scope ledger row.
`RULE_ID` gains `DR-\d+`; `ledgerProblems` counts a row covered when a behaviour cites its id.

## Files, states and re-runs

- All new files sit in `.rig/product/sprints/sprint-<N>/` beside `prd.md`; `prdPath` stays `prd.md`.
- `source.md` and `conversion.md` join the chart's approved files (`chartFiles`), so editing either after chart approval
  makes the chart stale. `conversion-review.md` stays out, like `chart-review.md`. `prd-approval.json` is denied to the
  model and listed as a CI human row; it is not a chart file.
- A sprint is **converted** when `source.md` exists and its normalised text differs from `prd.md`. The PRD approval is then
  required, whether or not `conversion.md` exists; a missing `conversion.md` in a converted sprint is itself a `map-missing`
  block finding.
- A re-run of `/rig:chart <N>` never rewrites `prd.md` or `source.md` once `source.md` exists. When the person edited
  `prd.md` during review, the PRD approval is stale: chart runs `prd check` and `prd map` again (a deleted criterion that
  the map names is a `map-id` finding to fix), asks for `/rig:approve prd-<N>` again, and stops. There is no second
  conversion.
- Chart runs `S prd ledger <N>` after the gap pass for every new chart, converted or not. `ledger-stale` applies to every
  sprint without a chart approval.
- `prd map` uses the ledger's line tolerance (3 lines, or within the block).
- A PRD that is not markdown (HTML, docx, PDF): the original is kept as `source.<ext>`, and the coordinator writes
  `source.md` as its plain-text rendering before converting; the map quotes `source.md`. The rendering itself is the one
  step a script cannot check, so the conversion reviewer also reads the original.

## Fixtures

The e2e chart fixture's PRD and `docs/prds/shopping-cart-app-prd.md` are rewritten in the template, and the fixture's
`requirements.md` is regenerated with `S prd ledger`. Skill-text specs change only where the text they pin changes (chart
step 1, the evaluator); `eval/chart.mjs --key sprint-a` keeps its dry-run fixture, now in the template.

## `/rig:init` and the journey

`/rig:init` and the journey's "write a PRD" hint point to `templates/prd-format.md` (copied to `docs/prd/` as
`sprint-<n>.md` when the person asks for a blank one). `docs/prds/shopping-cart-app-prd.md` is rewritten in the template as
the reference example, and the e2e chart fixture's PRD is too.

## Already-charted sprints

A sprint whose chart is approved keeps its PRD and its hand-written ledger; nothing re-runs. `ledger-stale` applies only
to sprints with no chart approval.

## Verification

- `scripts/prdformat.spec.ts`: each `prd-*` rule fails without the fix, on a PRD that states the id rules as a Data model
  paragraph (`prd-prose`) and passes once they are `DR-1`, `DR-2`.
- `prd map` specs: a conversion map that omits the "never reused" sentence blocks; one that maps it to `context` without a
  reason blocks; a dropped fenced example blocks.
- `prd ledger` spec: the generated rows for the shopping-cart PRD equal a checked-in expected ledger; `ledger-stale` blocks
  after `prd.md` gains an AC.
- Approval specs: `approve prd-N` is human-only, refuses on open findings, goes stale on an edit of `prd.md`, and
  `approve chart-N` refuses a converted sprint without it.
- Skill-text specs for chart step 1, the conversion mode of the evaluator, init and the template.
- Eval: `eval/chart.mjs --key sprint-b` (the prose id rules) also scores the conversion: the map quotes both rules, `prd.md`
  states them as DR or AC lines, and the criterion text keeps "1" and "never". Live runs are started by the person.
- `npm test` and `npm run typecheck`.
