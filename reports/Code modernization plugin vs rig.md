# Borrow the compass and the judge, not the journey

The code-modernization plugin is worth learning from for three things, and you should copy almost none of its modernization-specific machinery. The three things are: **one front door and one compass that always name the next command**, **verdicts computed by scripts from result files the model cannot type into success**, and **a hostile, booby-trapped codebase used as a test target**. rig is already well ahead of the plugin on enforcement, model pinning, cost measurement and automated testing. The plugin ships **no evals, no fixture codebases and no CI that runs its own tests**. Its evidence is 328 Python unit tests of its judging scripts, about 143 tests of its UI pane, and headless manual runs on 14 public codebases, written up as README prose. The plugin's real lesson for rig is narrower than "design the journey as commands", which rig already does with 17 skills that each end on a `Next:` line. The lesson is that **the plugin closes the gap between "a test was named" and "a test ran and passed"**, and it learned that from a failure on the JPetStore run. rig's traceability check and its "where am I" experience look weaker on exactly those two points. One caveat on framing: nothing in rig's repository records the plugin as an inspiration. A grep for "modernization" across the repo's docs and code returns nothing, and the stated sources are the AI-native SDLC playbook, Fowler, Devin and others. So the comparison below is on design merits, not on lineage.

## Thirteen commands and one artifact folder make the plugin's journey feel inevitable

The plugin is a strictly linear, file-chained ladder: `modernize` (front door) → `preflight` → `assess` → `map` → `extract-rules` → `review` → `brief` (human approval) → one of `uplift` / `transform` / `reimagine` → `verify` → `harden`, with `status` as the "where am I / what next" compass ([README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/README.md)). Alongside the **13 commands** it ships **8 agents, 6 Workflow scripts and a set of Python judging scripts, and no skills directory at all** ([plugin dir](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)). The coherence comes from four rules applied without exception. Every command opens by reading named files and stopping if they are missing ("the fix is `/code-modernization:modernize $system --source <path>`"). Every command ends by naming the exact next command. State lives only in `analysis/<system>/` and `modernized/`, so "a second person or a fresh session can run status and continue". And the front door asks a non-expert at most two pop-up questions, records the answers in `INTENT.md` "so nothing is asked twice", then behaves like `status` whenever analysis files already exist ([modernize.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/commands/modernize.md), [modernize-status.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/commands/modernize-status.md)).

Two design choices sit under that surface. The plugin lists **six points where a person decides**: the preflight answers, rules that look wrong, approving the brief, accepting any difference the proof finds, signing the proof, and applying the security patch. All six are enforced by command prose, not hooks. The hooks only watch: the hooks README says the hook layer "only watches. It does not block or rewrite any edit or command" ([hooks/README.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/hooks/README.md)). The brief is binding through a rigid per-phase block (`Command:`, `Modules:`, entry and exit checkboxes). Commands "may tick a box or add a note but never reword a criterion", and a proposed change goes on a `Proposed revision:` line ([modernize-brief.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/commands/modernize-brief.md)). The plugin also pins **no model anywhere**: a grep for `model:` across its commands, agents and workflows finds nothing, so quality depends on host defaults ([agents/](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization/agents)).

rig's ladder is structurally similar and in several ways stricter. It has 17 skills and 2 agents. The core path is `init → (chart) → start → plan → approve → build → test → pr`, with build, test and pr chained automatically after a single human approval ([skills/](../skills/), [README.md](../README.md)). rig's approval is mechanical where the plugin's is prose. `approval.json` hashes the spec, the plan and the frozen contract files, and it goes stale on any change. `/rig:approve` is `disable-model-invocation: true`. `/rig:pr` refuses without approval and a fresh passing `verify.json`. A PR that touches `approval.json` needs approval on GitHub from someone other than its author ([skills/approve/SKILL.md](../skills/approve/SKILL.md), [skills/pr/SKILL.md](../skills/pr/SKILL.md)). rig also pins models by role, with Opus as evaluator and Sonnet as architect, and has the CI `rig-check` job judge the change again using the checker from the base branch. The plugin has neither.

Where the plugin is plainly better is **discoverability**. rig has **no `/rig:status` or `/rig:help` skill**. "Where am I" is answered by `sdlc.ts status`, by the session-start hook's injection, and by the dashboard mod. GOAL's own open list asks whether that mod's API "still exist[s] in the current Claude Code" ([docs/GOAL.md](../docs/GOAL.md), [hooks/dashboard.tsx](../hooks/dashboard.tsx)). Several journey-relevant capabilities exist only in the CLI: `ready`, `queue next`, `report`, `readiness`, `risk`, `weight`, `carry`. `arch approve` and `app approve` must be typed as `! SDLC_HUMAN=1 node .rig/bin/sdlc.ts ...`, while `/rig:approve` and `/rig:waive` are slash commands ([skills/arch/SKILL.md](../skills/arch/SKILL.md), [skills/app/SKILL.md](../skills/app/SKILL.md)). The README is 499 lines. Install starts at line 292, after governance and eval disclaimers. The README's status line still says 0.6.0 while `plugin.json` says 0.7.0 ([README.md](../README.md), [.claude-plugin/plugin.json](../.claude-plugin/plugin.json)). Command names also split by design: `/rig:x` in plugin mode, `/rig-x` once vendored. The plugin's README puts "The path" table and a "Words you will see" glossary near the top. rig has more than a dozen concepts (intent, chart, sprint, ledger, tier, rung, sensor, floor, knownRed) and no glossary.

## Models produce, scripts judge: the plugin's sharpest idea, and the one rig half-has

The plugin's most distinctive trait is its proof pack. `scripts/proof_pack.py` computes **PROVEN / PARTLY PROVEN / NOT PROVEN** per module from six checks. Tests must have run, as parsed from JUnit XML or logs; "typed-in counts cap at gap". Every P0 rule must be backed by a test that **ran and passed**; "named, not run" and "claimed" do not count. The remaining checks are byte-level old-versus-new comparison through `compare.py`, at least ten fresh inputs, a canary, and source left untouched. Verdicts are recomputed on every run and never carried over. Open questions and sign-off "never change the verdict" ([proof_pack.py](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/scripts/proof_pack.py)). The verifier does its canary again on a scratch copy and grades it from its own result files, because "a `Canary:` line in the notes is a claim; the pack does not count it" ([modernize-verify.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/commands/modernize-verify.md)). The README's summary of the stance: "Modernization fails quietly: the new code passes the tests someone wrote, and differs on the inputs nobody thought of. So the proof is built from evidence a script can check, not from the model's opinion" ([README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/README.md)).

These rules came from failures. Commit d49ccb38, "a rule is tested only if a test that ran backs it", came from the JPetStore run, where **skipped tests had been counted as covering rules**. Commit f45794fa closed "3 ways uplift could come out PROVEN too easily", including typed baselines and edited tests. Its message admits that weakened assertions still cannot be detected ([PR 6309](https://github.com/anthropics/claude-plugins-official/pull/6309)).

rig shares the philosophy: one of its eight principles is "scripts decide, models advise" ([DESIGN.md](../DESIGN.md)). It has real equivalents. `S run --expect-fail` must fail before code is written. Red-proof runs new feature and bugfix tests on the base, where they must fail. Refactors must pass on the base both before and after. Traceability requires each B-number to be "named by a test" ([skills/build/SKILL.md](../skills/build/SKILL.md), [skills/test/SKILL.md](../skills/test/SKILL.md)). The notes suggest three gaps that map directly onto the plugin's hardening. First, the documented traceability rule is "named", which is the exact wording the plugin abandoned after JPetStore. Whether rig's `verify` also requires that the naming test executed and was not skipped was not checked in the scripts, and that is the first thing to confirm. Second, rig's mutation-diff, its nearest equivalent to a canary, covers only node and angular stacks, and "weak-red blocking" is deferred ([CHANGELOG.md](../CHANGELOG.md)). Third, rig has no first-class "can't prove" outcome. A stack whose test runner emits no parseable results has no equivalent of the plugin's rule that "zero executed = not proven".

The plugin's verdict vocabulary also gives people something they can sign. "PARTLY PROVEN because legacy cannot run" is information. A green tick with a hidden caveat is not. rig's `verify.json` is pass or fail per sensor. A three-state summary in the PR body, derived by script, would extend rig's existing PR-body evidence work (item 2 of the verification-evidence proposal, merged in 03aae26) rather than add a new layer.

## The plugin was tested by hand on 14 codebases; rig is tested by machine and still lacks proof of lift

The plugin's testing is more modest than its README suggests. It has two committed suites, and **both test the plugin's own code, not its prompts**. The first is `scripts/tests/`: 7 stdlib `unittest` files with **328 test functions** over the judging scripts, about 140 of them on `proof_pack` alone. The second is `tests/*.test.ts`: about 2,400 lines on Claude Code's own test kit (`claude plugin test`), using in-memory fake workspaces ([scripts/tests](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization/scripts/tests), [tests](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization/tests)). There is **no `evals/` directory, no committed legacy fixture, no golden output and no committed run log** ([plugin dir](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)). The marketplace CI in claude-plugins-official is policy and schema hygiene only: `validate-plugins`, frontmatter, licences, MCP URL liveness, and a Claude policy scan. **No workflow runs the plugin's unit tests, `claude plugin test` or `claude plugin eval`** ([.github/workflows](https://github.com/anthropics/claude-plugins-official/tree/main/.github/workflows)). The 1.0.0 PR's test plan reports "Script tests (303), pane tests (143), `tsc`, manifest validation and the frontmatter check pass". It also says the author "ran every command headlessly on 14 public codebases and a purpose-built hostile one" ([PR 6309](https://github.com/anthropics/claude-plugins-official/pull/6309)). The outcomes are listed in the README's "What it has been tried on" table: CardDemo ended NOT PROVEN, osCommerce PROVEN, JPetStore NOT PROVEN with 6 of 24 comparisons differing, and Spring PetClinic stopped at the plan gate. The README adds caveats: "the tester played that person" at approval gates, and "the same command can give different counts on a second run" ([README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/README.md)). One PR test plan also mentions a workflow script run "under node with the workflow globals stubbed: 75 assertions", but that harness is not committed ([PR 3869](https://github.com/anthropics/claude-plugins-official/pull/3869)).

rig's testing is far deeper:

| Layer | code-modernization | rig |
|---|---|---|
| Deterministic unit tests | 328 Python + ~143 TS, judges and pane only | 88 spec files / 14,104 lines over 8,648 source lines, plus 34 e2e/eval unit files |
| Prompt/skill text pinned | none | skill-text specs (`skilltext`, `chartskill`, `prskill`, ...) |
| End-to-end, no model | none | scripted journey from recorded snapshots, parallel worktrees, 5-stack onboarding with `--require all` |
| CI | marketplace hygiene only | 3 OS × 2 Node matrix, scripted e2e, dry evals; nightly live paired eval capped at $15 |
| Live behavioural evidence | manual headless runs, prose table | paired arms, hidden acceptance, review/chart/app/learn/wiki/ablation evals, scored by running |
| Hostile-input testing | booby-trapped repo; 100k-char ReDoS inputs on every parser | not found in the notes |
| Regression gate on quality | none | `eval/gate.mjs` exists, but `eval/baseline.json` is `{}` |

Sources for the rig column: [package.json](../package.json), [.github/workflows/ci.yml](../.github/workflows/ci.yml), [.github/workflows/eval.yml](../.github/workflows/eval.yml), [eval/gate.mjs](../eval/gate.mjs), [eval/baseline.json](../eval/baseline.json), [scripts/seeded.spec.ts](../scripts/seeded.spec.ts).

The asymmetry runs both ways. rig measures what the plugin never does, and what rig measures is unflattering. "No eval has shown a lift over plain Claude Code yet." rig with Haiku costs $0.087 per task against $0.032 for bare Haiku, and takes 8.2 minutes against 2.4. The review eval is saturated, with 100% recall for both models, so it "still cannot rank reviewers" ([docs/GOAL.md](../docs/GOAL.md), [README.md](../README.md), [eval/results/2026-10-29-review.md](../eval/results/2026-10-29-review.md)). The plugin publishes NOT PROVEN outcomes but never compares itself with a no-plugin baseline. rig is more honest in kind; the plugin is more legible in presentation. Two of the plugin's testing practices fill clear gaps in rig.

The first is the **hostile codebase**. The plugin planted instructions in comments, the README, CLAUDE.md, a settings file, a marker-dropping script and shell-syntax filenames, and reported "nothing obeyed, source unchanged, credential masked". Every agent carries an "Untrusted content discipline" section ([agents/legacy-analyst.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/agents/legacy-analyst.md)). rig's init scouts, wiki builder, architect and reviewers all read target-repo text, but the notes found no injection fixture and no equivalent discipline paragraph.

The second is `hostile.test.ts`, which feeds **100,000-character lines to every reader** to rule out regex backtracking freezes ([tests](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization/tests)). rig parses PRDs, conversion maps, coverage tables, wiki citations and user-authored `rules.json` regexes. Some of those run inside Stop and PostToolUse hooks, where a freeze stalls the session.

## What to adopt, in order, and which items need an eval first

The list below applies rig's own rules: native first, thin layer, nothing added or cut without evidence, and the target of under 45 minutes and $8 per Spec-2-sized change. Items marked "no eval" are correctness or presentation fixes that put no new prompt choreography in front of the model. Items marked "eval" add model-facing behaviour, and GOAL's rule requires a measured lift before they stay.

| # | Recommendation | Why (from the notes) | Evidence needed |
|---|---|---|---|
| 1 | **Make traceability count only tests that ran and passed**: a B-number named by a skipped, disabled or never-executed test fails, and zero executed tests is a failure, never a pass | The plugin's JPetStore failure (d49ccb38); rig's documented rule is "named by a test" | No eval. Read `verify` first; if it already parses run results, close as done. Add a seeded spec with a skipped naming test |
| 2 | **Hostile-input spec for every rig parser and hook-path regex** (100k-char lines, pathological patterns) | Plugin `hostile.test.ts`; rig's parsers run inside blocking hooks | No eval; deterministic spec |
| 3 | **Run `claude plugin validate` in `ci.yml`** | `npm run validate` exists but is not in CI; the official marketplace's required check is this validator | No eval |
| 4 | **Fill `eval/baseline.json` from the 2026-10-31 runs** so the nightly gate enforces something | Gate logic is sound; with `{}` every arm is "not enforced" | No new eval; uses existing results |
| 5 | **A compass: `/rig:status` that doubles as the front door** (no active change: say where you are and the one next command; with state: five lines, as the plugin does) | rig has no on-demand "where am I"; the dashboard depends on an unverified mod API (GOAL Open); returning after a week is the weakest point of the journey | Light. It wraps existing `sdlc.ts status --journey`, so it adds no gate. Do it if the mod or status-line check fails, and record that result as the evidence |
| 6 | **Restructure the README around "The path" plus a glossary**; fix the 0.6.0 status line and the missing `upgrade` in the layer box; give `arch approve` and `app approve` the same slash form as `/rig:approve` | The plugin's README puts the path and "Words you will see" first; rig's Install is at line 292 | No eval; docs and consistency only |
| 7 | **A hostile fixture repo plus an "untrusted content" paragraph in the architect, evaluator, review brief and init scout briefs** | Plugin's booby-trapped run; rig agents read target text | Deterministic half (secret masking, nothing written outside the allowed paths, hooks still fire) needs no eval. Whether the paragraph changes model behaviour does: run the fixture with and without it, live, before keeping it |
| 8 | **A script-computed three-state verdict line in the PR body** (proven / partly proven: which checks could not run / not proven) | The plugin's verdict is the thing a person can sign; extends merged item 2 (03aae26) | No eval for the derivation; reuses `verify.json` |
| 9 | **A cross-stack canary**: the verifier makes one break in a scratch copy and the script confirms the suite goes red, generalising mutation-diff beyond node and angular | Plugin's canary is graded from result files; rig's weak-red blocking is deferred | **Eval**: the seeded `bad/tautological-test` and `unchanged-test-edited` cases must show it catches what red-proof misses, at under ~10% added cost |
| 10 | **Circuit breaker for fan-out builds** (stop a batch whose success rate falls below two-thirds; fix the playbook, don't add agents) | Plugin's uplift fan-out rule | **Park** until autonomy rung 2 or above runs batches; no current evidence of need |

The two **"legacy is the oracle"** rules belong in rig's refactor path as skill text. The first: when existing behaviour and the spec disagree, the test asserts current behaviour and the discrepancy is flagged separately. The second: unimplemented behaviours are marked skipped and named, never deleted. rig's refactor type already requires tests to pass on the base before and after, so this is a clarification, not a new gate. It still counts as model-facing text, so treat it like item 7: cheap to add, and kept only if a refactor case in the paired eval shows fewer silent behaviour changes.

Some things rig already does better and should keep. Approval is frozen by hash rather than bound by prose. Blocking sensors run at Stop, at commit and push, and again in CI with the base branch's checker. Models are pinned by role, with Opus evaluating Sonnet. Cost is measured against a no-rig baseline. The skill-text specs pin required clauses. Deterministic e2e runs in CI on three operating systems. The plugin has none of these. Its own README concedes that "the hard guarantee is the operating system: a read-only mount, or a sandbox" ([README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/README.md)).

Some things rig should not copy. The modernization stages themselves (`assess`, `map`, `extract-rules`, `transform`, `reimagine`, byte-equivalence and `harden`) fall outside GOAL's stated scope. GOAL describes a general harness whose brownfield support is "join at init, baseline the debt, wiki the code" ([docs/GOAL.md](../docs/GOAL.md)). Under native first, a team modernizing an estate should run the plugin itself, not have rig reimplement it. The plugin's fan-out scale (**466–647 agents and about 8.8M tokens for a 30,000-line estate**) is incompatible with rig's $8 target ([PR 6309](https://github.com/anthropics/claude-plugins-official/pull/6309)). A per-rule review deck of pop-ups would add stops after rig worked to remove them, cutting `/rig:start` from 18 questions to none for settled intents. The plugin's habit of testing prompts only through manual runs reported in README prose would be a regression for rig.

Not copying `claude plugin eval` wholesale needs a native-first argument. It is the native tool, and it provides isolated sessions, three runs per case and a with/without baseline arm. But it has "no custom-code graders", and rig's paired eval scores by running `npm test` and hidden acceptance tests ([plugin evals docs](https://code.claude.com/docs/en/plugin-evals.md)). It fits narrow skill-level checks, such as "does `/rig:start` on a settled intent ask zero questions" (a `tool_used` grader on AskUserQuestion), better than rig's outcome evals. Moving those narrow checks to the native runner would let rig delete custom code. That is the kind of pruning GOAL allows, because native covers it.

## Conclusion

The plugin and rig fail differently. The plugin looks rigorous and hides how little of it is regression-tested: its prompts have no evals and its own tests never run in CI. rig is rigorously tested and hides how hard it is to follow: no status command, a 499-line README, and a working tree whose regression gate and triage files are both `{}`. The useful transfer is not the command-journey pattern, which rig already has. It is the plugin's insistence that every success claim be re-derived by a script from result files. "Named" is not "ran", a canary line is a claim until re-run, and "could not prove" is a verdict, not a failure to hide.

The cheapest high-value moves (items 1–4 and 6) are deterministic, need no eval, and add almost no prompt text. That fits a harness whose own evals say the model is not the weak link at the current task difficulty, and whose biggest open risks are a quiet false pass and a person who cannot find the next step. Everything that adds words in front of the model, such as the untrusted-content discipline, the oracle rule and a generalised canary, should go through the seeded-bad and hostile fixtures first. Without that, rig repeats the plugin's one real weakness: claims about prompt quality that nothing checks.
