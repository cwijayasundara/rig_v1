# Cutting rig down to its core

rig's core idea is sound and well matched to its sources, but rig is not thin, and roughly half of it is process, telemetry and UI that none of the four sources ask for. The sources prescribe a small set of things: a short CLAUDE.md, plan before build, advisory skills backed by deterministic hooks, fast computational sensors in-session, one verification gate, a human release gate, and a loop that improves the harness when a mistake repeats ([Anthropic playbook](https://claude.com/resources/articles/the-ai-native-sdlc-playbook); [Fowler, harness engineering](https://martinfowler.com/articles/harness-engineering.html); [Fowler, sensors](https://martinfowler.com/articles/sensors-for-coding-agents.html)). rig implements all of that, then adds **7,840 lines of authored harness TypeScript, 595 lines of skill prose across 22 skills, 5 agents, 40 CLI subcommands, 10,149 lines of specs, and a separate 3,086-line `brain/` plugin**, built over 596 commits in 14 days. The author's premise that the cost article shows a small model plus harness matching a larger model is also wrong for the Claude family. That article compares two OpenAI models, never tests Haiku, and shows the harness adding about 7x cost on the stronger one ([Jain, are harnesses worth the cost](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html)). rig is fit for purpose in its guardrail core and over-engineered everywhere else. A defensible target is about 2,000-2,500 lines of scripts, about 6 skills and no UI or memory layer, with an A/B run added to justify whatever stays.

## What the four sources actually prescribe

The Anthropic playbook (dated 2026-08-21 in the fetch) argues that code generation is no longer the bottleneck and replaces the linear SDLC with a loop in which each stage commits an artifact the next stage reads. Its artifacts are few: `intent.md`, `spec.md`, `plan.md`, tests and CI output, `REVIEW.md`, and in Maintain a config file of response bands. Its 16 plays lean on Claude Code built-ins: plan mode, auto mode, worktrees, `.claude/agents/`, skills, hooks in `settings.json`, and a CLAUDE.md kept to about a page. Two of its sentences define the guardrail philosophy: "A skill is an advisory control while a hook is the deterministic layer behind it," and build-phase hooks "should be fast and scoped to the file that changed," with heavier checks "at the commit or the PR" ([playbook](https://claude.com/resources/articles/the-ai-native-sdlc-playbook)). It does prescribe a few narrow scripts, a production-gate hook and a deterministic detection script with unit tests, but no wrapper, no wiki or memory plugin, no change-record system, and no spend tracker. Its only budget language is a spend limit on Claude Security scans and an API key with budget for evals. It names no models in its body, so the "Haiku reads, Sonnet writes, Opus reviews" routing is rig's own. Measurement appears only as leading and lagging indicators per play and a single metric with a stable baseline. (The notes' caveat applies: the article was read through a summarising fetch, so wording is high-confidence rather than byte-checked.)

Fowler's harness-engineering article supplies the vocabulary: guides steer before the agent acts, sensors observe after, and computational checks (linters, type checkers, fast tests) are "deterministic and fast" while inferential ones (LLM review) are costlier and probabilistic. It says to keep quality left, run inferential checks not "on every commit," and treat the harness as "an ongoing engineering practice." It warns that guides and sensors must not contradict each other and that no sensor can catch misunderstood instructions or unnecessary features ([harness engineering](https://martinfowler.com/articles/harness-engineering.html)). The sensors article adds three cadences (continuous in-session, again in CI, slower drift detection) and the sharpest warning for rig's situation: "I worry about feedback overload for the agent, sending it into a spiral of over-engineered refactorings." It also asks which guides can be deleted once sensors are trusted ([sensors](https://martinfowler.com/articles/sensors-for-coding-agents.html)). Neither article gives a cap on sensors or any size benchmark, so "how big may a harness be" is a judgment the sources do not settle.

## The cost article does not say what the premise assumes

The brief assumed the cost article compares Haiku with Opus. It does not. Naresh Jain's study (13 October 2026) ran 10 paired runs per arm of two OpenAI models through Codex at low reasoning effort, on one greenfield Java backend-for-frontend, scored by 178 hidden acceptance tests. Claude Sonnet 4.6 and Opus 4.6 appear only in unmeasured exploratory runs where they finished the task unaided, and Haiku is not mentioned ([cost article](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html)). The measured result is mixed:

| Model | Harness | Tokens | Time | Est. cost | Accepted |
|---|---|---|---|---|---|
| GPT-6 Sol (frontier) | yes | 11.3M | 19m53s | ~$2.68 | 10/10 |
| GPT-6 Sol | no | 1.08M | 6m51s | ~$0.41 | 10/10 |
| GPT-6 Luna (cheap) | yes | 22.9M | 35m | ~$0.27 | 10/10 |
| GPT-6 Luna | no | 5.86M | 15m56s | ~$0.09 | 3/10 |

Two readings follow. For the frontier model the harness cost about 10.5x the tokens and about 7x the dollars for zero acceptance gain. For the cheap model it turned 3-in-10 into 10-in-10, and harnessed Luna was about 33% cheaper than unharnessed Sol. The author's own conclusion is that "a behavioral harness is not an automatic win for every model on every task" and that capability changes "when" sensors run, not whether they are needed: continuously for cheap models, possibly as one final gate for strong ones, a mode the author "plans to test." The study also excludes the cost of writing and maintaining the contracts, tested a harness built from OpenAPI/AsyncAPI contracts and mocks rather than process gates, cannot separate guides from sensors, and covers one task. It therefore cannot support a claim that rig's process layer lifts a small Claude model, and the word "thin" is not Fowler's: the article describes a full harness and never tests a thin one. The pattern rig can legitimately borrow is cadence scaled to model grade, and rig already did so with its opt-in `behavioral` block, the one feature derived directly from this article.

## What rig implements today

The measurements below come from the repo at branch `e2e-live-under-20min`. Authored harness code is 7,125 lines across 43 script modules plus 715 lines of mod UI, and the largest files are `core.ts` and `sdlc.ts` (500 each), `check.ts` (466), `model.ts` (452), `sensors.ts` (385) and `hooks.ts` (363). Around it sit 22 skills (9 to 60 lines each), 5 agents (115 lines), 17 templates (1,130 lines, including four CI workflows of 103 to 217 lines), 7 registered hook events, 8 mod slash commands, and 877 passing tests (861 specs plus 16 e2e unit). Specs total 10,149 lines against 7,840 of code, about 1.4 test lines per code line. A user must hold roughly six nouns (intent, change, tier S/M/L, gate, `sensors.json`, `.rig/` evidence) and about 22 `/rig:*` commands. `brain/` adds 3,086 source lines, 1,549 spec lines and 10 more hook commands, so a turn with edits can spawn about 14 Node processes. The README calls rig "a thin control layer" that "adds very little of its own," while `scripts/size.spec.ts` caps the harness at 11,000 lines, a cap that the CHANGELOG records was once 6,060. The README says 20 skills and the repo has 22, a small sign that the surface outgrew its documentation.

Mapped against the sources, the notes classify the pieces as follows. The **core that the sources justify** is the Stop and PostToolUse gate running fast typecheck and tests on the turn's diff, the secret scan, the test-tamper, suppression and lowered-threshold sensors (the clearest match to "fix the code, not the test"), the verification-before-done check, git hooks, the base-branch CI recompute (`rig-check`), a few path-injected guides, and the `rule` skill as the steering loop. The **optional but source-aligned** pieces are drift sensors (quality counts, ratchet), incident-to-eval, and one human approval before build and before merge. The **inventions** are tiers S/M/L and type-by-tier routing (no source mentions tiers), story points, spend budgets with downshift and a `refs/rig/spend` ledger, the sprint chart layer (PRD, architecture, decompose, test plan), the mission-control band, and the whole `brain/` plugin. By file sizes the notes estimate that **55-65% of non-test code** serves process, UI or telemetry no source requests; this is an inference from names and sizes, since not every script body was read.

## Fit for purpose: the guardrail core passes, the process layer does not

Judged against the stated purpose, a wrapper that makes Claude Code follow the playbook, rig fits where it enforces and overreaches where it prescribes. The enforcement design matches the sources closely: no hook calls a model, deterministic checks decide and models advise (DESIGN.md principle 5), heavy checks move to the verify stamp and CI, and tamper detection protects the verification loop the playbook cares most about. Its cost diagnosis is also honest. The repo's own proposal (`docs/proposals/2026-10-08-why-slow-and-the-fix.md`) finds the headline spend was not rig's hooks: of about **$997 recorded over a week, 68% ($679) was Opus 5.5**, driven by Opus security reviews firing on every Stop, 20 user-scope plugins producing a 56.7k-token first-call prompt, and an Opus coordinator holding about 250k tokens through a subagent loop whose hand-backs re-fired every Stop hook. The fixes it names are settings (`ENABLE_STOP_REVIEW=0`, project-scoped plugins, a Sonnet main thread). The rig repo's CLAUDE.md now encodes them as a model table, one review per change and a 60-line brief limit, which is native configuration doing what the spend machinery in `spend.ts` and `metrics.ts` was built to do. The notes caution that CLAUDE.md's line "one week of building this repo cost $1k" conflates the cost of building the harness with the cost of running it, and no measurement of rig's per-change cost on a target repo exists beyond the live e2e at about $1.20 and 14-16 minutes on Haiku.

Three divergences from the sources matter. First, the playbook says review findings "do not approve or block a PR on their own," yet rig's ratchet loops implementer, sensors and reviewer until no critical or high finding remains. Second, Fowler's feedback-overload warning applies to a harness that stacks size, layering, tier, scope, quality-count, contract and tamper sensors; the repo records no false-positive rate, so whether they are noisy is unmeasured, though the CHANGELOG is full of fixes for model-driven failures (rewrote a file, ended the turn early, ran on the wrong branch) that suggest long multi-subcommand skill text is itself a failure source. Third, rig spreads human attention over design, spec, plan, chart, tier, impact and budget approvals, where the playbook asks for one plan acceptance and one production gate, and Fowler wants human input directed "to where it matters most." The cost study's lesson also cuts against the default: rig runs its full pipeline continuously, even for an Opus tier-L change, which is the configuration where the study found overhead without benefit. Finally, no baseline-versus-harness run exists in the repo; the only paired designs are `brain/evals`, with no recorded results. The e2e suite proves rig's process completes against a hidden acceptance test (`tests/e2e/acceptance/shop.mjs`) but, with rig always on, cannot show any lift. The author has also cut once before (the wiki and learn loops were removed "to keep the harness lean," then the wiki returned as `brain/`) and does not run rig on its own repo, so there is no dogfooding signal about its build and plan skills versus superpowers.

## A concrete simplification plan

Keep the guardrail core, about 2,000-2,500 lines of scripts by the notes' estimate: the Stop and PostToolUse hooks driving a slimmed `check.ts`, `sensors.ts` and `model.ts`; `verify.ts` and `runs.ts`; `githooks.ts`; the `rig-check` workflow with base-branch recompute; the three short guides; the `approve`/`waive` digest logic reduced to a plan gate and a merge gate; and the opt-in `behavioral` block. Keep about six skills: start (intent plus plan), build, test, pr, rule, init. Delete the rest, with approximate line counts from the notes: `brain/` (about 4,600 including specs, replaced by CLAUDE.md and Claude Code auto-memory, which this very repo already uses); the mod UI and the SubagentStart/Stop hooks that exist only to feed it (715 lines); spend, metrics, scorecard, timing, points, context and stale (about 1,000 lines, replaced by `/cost`, `/context` and a pinned model in `.claude/settings.json`); the chart layer and its four skills (about 450); tiers, routing, ratchet, checkpoint and slices (about 450, replaced by the model table already in CLAUDE.md); scopes, sparse base, preflight, toolchain, vendor and initbaseline (about 850, kept only if monorepos or standalone installs matter); and the maintain workflows and incident/metrics/next skills (about 900 plus 190 of skill text, with the incident-to-eval idea survivable as one small script and workflow). The five custom agents give way to built-in Explore, Plan and general-purpose agents. Total removal is on the order of **9,000-10,000 production lines and 6,000-7,000 spec lines**; these are the notes' estimates, not measurements.

The native replacements are specific. Plan, spec and design skills give way to plan mode and superpowers brainstorming and writing-plans; build and test to superpowers executing-plans, test-driven-development and verification-before-completion; review to built-in `/code-review` and `/security-review`; diagnose to systematic-debugging (the repo already folded one in); the band to the status line; memory to auto-memory; and branch isolation to worktrees. What has no native equivalent, and justifies rig's existence, is the short list of path-triggered guide injection, test-tamper and suppression sensors, evidence deny rules, the base-branch CI checker, and human-only approve and waive with staleness hashing. Before keeping anything beyond that, run the experiment Jain's design implies and the repo has the parts for: the same task set with Haiku plus rig's guides and sensors, Haiku bare, and a stronger model bare, about 10 runs per arm, hidden acceptance suite, tokens and dollars recorded, and a third mode with the sensors run only as a final gate. Even a favourable result would be weak evidence (one task type, small samples), so a feature that cannot show a lift should be cut rather than defended.

## Conclusion

The sources do not argue against harnesses; they argue for small, deterministic, cadence-tuned ones, and they treat the harness as something to prune as sensors earn trust. rig's mistake is not its guardrails but treating the playbook's six stages as a product to reimplement, which produced a state machine whose own failure modes need still more harness. The more useful lesson from the cost article is that harness weight should follow model grade and be measured: the same checks that rescued a cheap model were pure overhead on a strong one. The repo's own history says the same thing, since its $1k week traced to plugin hygiene and an Opus coordinator, fixed by settings that now live in a 40-line CLAUDE.md.

The open question is what rig's real job is. If it is a guardrail kit for small-model teams, the cut above makes it sharper and cheaper to prove. If it is an end-to-end sprint-and-spend product, it is a different product from the one the sources describe, and the "thin wrapper" label should go.
