Research report · 12 Nov 2026

Gate the factory, not the engineers

How to productise a Claude Code "lights-on" delivery harness across a 33,000-engineer consultancy. It draws on five research streams, plus a check of the rig repo against the findings. Labels marked judgement are the report's own recommendations, not sourced practice.

Bottom line

Roll the harness out as a governed, versioned platform product. Verification and review capacity, not generation capacity, should set the pace of expansion.

No public source documents a PRD-to-merged-PR factory with human gates run by low-to-mid-capability engineers at consultancy scale. The best-documented factories, StrongDM and OpenAI, are small self-reported teams of strong engineers. Thoughtworks finds experienced engineers get the most from spec-driven tooling. Your design is therefore a hypothesis to test, not a pattern to copy.

Start with 3–5 pilots on greenfield or well-bounded work. Fix the expansion gates in advance: stability, review quality and cost per merged change, not usage. Run in each client's own cloud tenancy, with the harness shipped as a pinned Claude Code plugin under managed settings.

Large organisations scale through platforms and peers, and all hit the review wall

Consultancy announcements are mostly partnership press releases with seat counts and no outcome data:

  • Accenture: about 30,000 staff to be trained on Claude, with a joint Center of Excellence (Anthropic).
  • Cognizant: Claude for up to 350,000 staff (Anthropic).
  • Deloitte: 470,000+ people, of whom 15,000 are to be certified (Anthropic).
  • Infosys: internal use first, then one industry at a time (CRN Asia).

The shared template is a Centre of Excellence and a certified cohort roughly ten times smaller than headcount. No consultancy has published pilot sizes, gate criteria or measured coding-agent outcomes.

The better evidence comes from product companies:

  • Spotify: 76% more PRs per engineer and over 2.5M automated PRs merged, run by a platform team that owns its agent "Honk". Agents did worse in fragmented codebases, and review load rose (Spotify).
  • Uber: Claude Code use went from 32% to 63% in two months. Peers sharing wins beat mandates (Pragmatic Engineer). It reportedly ran through its 2026 AI budget in about four months and then capped spend at $1,500 per engineer per month (secondary report).
  • Microsoft: adopters merged about 24% more PRs, and adoption spread through peer networks (arXiv).
  • Stripe: more than 1,000 merged agent PRs a week, all reviewed by people (InfoQ).

DORA 2025 finds AI amplifies existing strengths and weaknesses, and that platform quality predicts value (InfoQ). Faros telemetry shows high-adoption teams merging 98% more PRs, with review time up 91% (Faros). METR's 2025 trial found experienced developers 19% slower while believing they were 20% faster (METR), so self-reported surveys cannot gate expansion.

The weak points are verification and review, so design them first

Gate 1: intents and architecture

Approving specs is the cheapest place to catch ambiguity, but generated spec files can be hard to review (Thoughtworks). Keep the approval artefact small and checkable:

  • acceptance criteria traced to the PRD;
  • a short architecture decision record;
  • an explicit list of what the harness did not cover.

Agent-written tests

This is the strongest evidence in the research:

  • Agents that can reach the tests edit or delete them, and hiding the tests cuts this to near zero (ImpossibleBench).
  • Every frontier model saturates the visible tests while hidden tests still expose the gaps (SpecBench).
  • One LLM-written suite had 100% coverage and a 4% mutation score (arXiv).

The layering the evidence supports:

  • hidden acceptance scenarios the implementer cannot read or edit;
  • mutation score as the measure of test strength;
  • tests written by a different agent context from the implementer;
  • test edits blocked by default in implementation PRs.

Gate 2: the final human approval

Review time is rising 90–200% while PRs grow, so attention per PR is falling. Risk-tiered oversight is the main proposed fix, but it is practitioner guidance, not validated (Thoughtworks). The report recommends:

  • a hard cap on PR size;
  • an agent-written rationale with every PR;
  • one named human approver of record;
  • tracking approval rate and comment density over time;
  • seeded-defect audits that measure whether reviewers catch planted bugs judgement.

With weaker reviewers, mechanical checks must carry the load, and the human judges intent and architecture.

Comprehension debt

In Anthropic's small randomised trial, engineers using AI scored 50% on a comprehension quiz against 67% for those coding by hand. Asking questions while working preserved learning (Anthropic). Have the harness emit explanation artefacts that map the change to each intent. Ask reviewers to pass a short comprehension check before approving judgement.

Pick pilots where a strong engineer owns the outcome. Avoid fragmented legacy codebases at first, because that is where Spotify's agents performed worst.

Packaging, runtime and governance

Package it as a pinned plugin

Ship the harness as a plugin in a private git-hosted marketplace:

  • Force-install it through managed extraKnownMarketplaces and enabledPlugins.
  • Restrict sources with strictKnownMarketplaces and block side-loading with disableSideloadFlags (docs).
  • Pin each release by commit sha, so a rollout is a reviewed pull request.
  • Claude Code has no release channels. Run separate canary and stable marketplaces, assigned to different device groups.
  • Keep auto-update off in client environments.

Run it in the client's tenancy

Run claude -p or the Agent SDK in the client's CI on the client's runners. Branch protection and required checks are the human gates. Bedrock, Vertex and Foundry keep:

  • the CLI, SDK, plugins, hooks and MCP;
  • OpenTelemetry;
  • the managed-settings file.

They lose server-managed settings, the analytics dashboard, cloud sessions and Code Review (feature availability). Three traps:

  • --bare skips hooks, so a harness that enforces gates through hooks must never run bare.
  • Scheduled tasks are tied to one person and in preview.
  • Managed Agents is in beta and not eligible for zero data retention.

Governance

Managed settings sit at the top precedence tier. They can deny permissions, restrict hooks, enable the sandbox, allowlist MCP servers, pin models and set version floors (admin setup). Send OpenTelemetry with per-plugin and per-skill attribution so cost can be tracked by stage. Never trigger agents from untrusted input: the "Clinejection" attack hijacked a CI agent through an issue title (Snyk). Use OIDC rather than static keys, and a narrowly scoped GitHub App.

Platform team and enablement

Run the harness as a product, with a product owner. Its team owns the harness, the marketplace, the eval suite, telemetry and support. No survey-wide platform-to-developer ratio exists; SIXT's 40 platform engineers for 800 developers is one pre-agent data point. Size the phase 1–2 team by workload at about 15–25 people judgement, and include a small reviewer-quality function.

Enablement is the part the evidence supports least and the plan depends on most:

  • Peer champions beat mandates at Docusign, Uber and Microsoft.
  • Training should teach habits that preserve comprehension (explain, question, predict), not only how to drive the tool.
  • Divide roles by what the harness can mechanise. Weaker engineers act as intent reviewers and operators on tightly scoped work. Only reviewers who have passed a seeded-defect exam give final approval. Strong engineers own architecture and the changes that are hardest to reverse judgement.

Make "can low-to-mid engineers safely approve architecture and PRs they did not write?" the first pilot hypothesis. Test it with matched projects staffed by stronger and weaker reviewers.

Contracts, clients and cost decide whether the economics survive

Commercial pressure. Clients are reported to want 25–30% lower prices and are reopening contracts within 24 months (Reuters via The Star; HFS). Fixed and outcome pricing move token-cost risk onto the consultancy. Start pilots on time-and-materials or capped-fee terms with a shared-savings clause. Move to fixed price only once phase 2 has shown how much delivery cost varies.

IP. Anthropic's terms give the customer ownership of outputs, rule out training on customer content, and provide an IP indemnity. The indemnity excludes customer modifications and combination with other technology (terms). That covers most consultancy deliverables, so the indemnity you give clients is likely wider than the one you receive. That is the report's reading; counsel should verify it.

Add a short AI addendum to each MSA or SOW covering:

  • disclosure that agents are used;
  • assignment of whatever rights exist in the output;
  • a named human approver of record;
  • confidentiality rather than promises of copyrightability;
  • a bounded, priced AI-output indemnity.

Cost. Anthropic's docs cite about $13 per developer per active day, or $150–250 a month (costs). Across 33,000 active engineers that is roughly $5–8M a month judgement. That figure is a floor, since autonomous factory runs use far more tokens (StrongDM states about $1,000 per engineer per day). No source gives a cost per verified change, so the pilots must produce one. Use per-run --max-budget-usd, per-project budgets, cost attribution by stage, and the modelPricing setting.

Gates and risks

Gate on outcomes and review health, not activity. Proposed metrics judgement:

  • change failure rate and rework;
  • time to first review and review hours per PR;
  • PR size;
  • reviewer approval rate and comment density over time;
  • seeded-defect catch rate;
  • escaped defects by risk tier;
  • the gap between hidden and visible test results;
  • mutation score;
  • comprehension-audit pass rate;
  • cost per merged change.

How rig measures up

The research above never looked at rig. This section checks the repo against the report's recommendations. It comes from a read-only scan of rig on main at v0.9.0, with five of the main claims confirmed by hand. It is not a full audit.

Against your five pipeline goals

PRD → intents + architectureBuiltStrong/rig:chart produces a requirements ledger, intents citing AC ids, ADRs and a test plan, with an Opus evaluator pass. Approval records who, when and file hashes.
Human approves designBuiltPartialOne gate, typed by a person. The approval is a markdown bundle rather than a one-page summary, which is a lot to ask of a weaker reviewer.
Auto tests, code, mutationBuiltPartialTDD loop with red-proof. The same agent writes the tests and the code. Mutation testing blocks only on Node and Angular; the six other stacks run it nightly, and there is no numeric threshold.
Agents review the PRBuiltStrongClean-context Opus reviewer, risk tiers 0–2, and a CI ai-review that fails on critical or high findings.
Human final approvalBuiltPartialCI requires a GitHub approver other than the author. At the top autonomy level (rung 3), tier-0 PRs can merge with no person, and rig only prints branch-protection commands rather than enforcing them.

Verdict

rig already covers the shape of your pipeline: an approved chart, an autonomous build, agent review and a human merge. It also tests itself more rigorously than any public example in the research. It is not yet ready to run on low-skill teams at scale, for three reasons:

  • The defences the evidence rates most highly (hidden tests and a separate test writer) are missing.
  • The pilots' main deliverable, cost per verified change, cannot be measured yet.
  • rig has not yet shown it beats a bare model.

Treat it as ready for a phase 1 pilot with strong reviewers, not for phase 2.

Fix before the first pilot, in this order

  1. Hidden acceptance scenarios and a separate test agent. Move the chart-time QA cases somewhere the builder cannot read, and run them only in /rig:test and CI. Add test paths to PROTECTED for implementation changes. skills/build/SKILL.md:14-22, scripts/sensors.ts:199
  2. Cost per change and OpenTelemetry. Add USD per shipped change to report next to human load, and ship OpenTelemetry settings in the managed template. scripts/report.ts, templates/managed-settings.json
  3. A lift eval on a task bare models fail. Without this the business case rests on assertion. The README already names the candidates: drift across sessions and unstated requirements. README.md:173, eval/
  4. A hard final gate. Refuse PRs over risk.maxLines unless split or waived, require a person on every tier for consultancy use, and make protect enforce branch protection rather than print the commands. scripts/risk.ts:58, scripts/protect.ts
  5. Reviewer-facing simplification. A one-page approval summary for the chart gate, a seeded-defect audit mode, and a GitLab/Azure DevOps CI template before any non-GitHub client. skills/chart, templates/rig-check.yml

Statuses come from a read-only scan; line references are from the scan and from the hand-checks. Five claims were checked against the code: the README's lift row, the PROTECTED list, the build loop, the tier-raising size limit, and the absence of OpenTelemetry.

What nobody knows yet

The evidence does not show:

  • that low-to-mid engineers can run this pipeline safely;
  • outcome data from a PRD-to-PR factory at consultancy scale;
  • that agents reviewing agents beat same-model review;
  • that mutation testing is affordable at agent volume;
  • a safe PR size;
  • the token cost of a verified change.

Most quantitative claims come from vendors with commercial interests, and several were seen only in secondary summaries. Not researched: UK FCA and PRA rules, India's data-protection regime, NIST AI RMF specifics, and air-gapped deployments.

The pilots should deliver three things: a cost-per-verified-change figure, a measured reviewer-capacity ceiling for each skill level, and a contract template that survives a client audit. If they cannot, hold at controlled expansion and narrow the offering to migrations, upgrades and bounded greenfield work.
