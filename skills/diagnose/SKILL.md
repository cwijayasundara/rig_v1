# Diagnose $0
Run each sdlc.ts command as its own Bash call (no `cd`, pipes, redirects, `&&` or variables); read files with Read and Grep; one-line commit messages. **Subagents:** run them in the foreground and wait; never end your turn while one is running.
1. **Build a feedback loop first.** No hypothesizing until you have a tight loop that goes red on *this* bug; everything after this step just consumes it. (Adapted from Matt Pocock's `diagnosing-bugs`, MIT.)
   - Read `intent.md`; note `git rev-parse HEAD` now (an incident eval in step 6 uses it as its base). **Redact every secret** in commands, output and captured artifacts you show or record: write `<REDACTED>` in its place and keep credentials in environment variables, never in the text; build the loop, trying in roughly this order: a failing regression test at the seam that reaches the bug; a curl/HTTP script against a dev server; a CLI run on a fixture diffed against a known-good snapshot; a headless browser script; replay of a captured trace or payload; a throwaway harness around the one code path; a property/fuzz loop over many inputs; a bisection harness (`git bisect run`) between two known states; a differential loop (old vs new version or config, outputs diffed).
   - The loop is done when you can name **one command** you have already run at least once (show the invocation and its red output, redacted) that fails for the reported reason - deterministically, or at a raised reproduction rate that makes it debuggable. A failing regression test goes through the recorder: `sdlc.ts run --expect-fail -- "<test command>"`, so the red run is on record. **Tighten it**: faster (narrow the scope, cache setup), sharper (assert on the specific symptom, not "did not crash"), more deterministic (pin time, seed randomness, isolate filesystem and network); a slow flaky loop barely counts. **Non-deterministic bugs:** raise the reproduction rate until it is debuggable - loop the trigger many times, parallelise, add stress, narrow timing windows; a 50% reproduction rate is debuggable, 1% is not. **If you cannot build a loop**, stop and say so: list what you tried and ask the person for (a) access to an environment that reproduces it, (b) a redacted captured artifact (HAR, log dump, recording), or (c) permission to add temporary production instrumentation. With no loop, do not proceed to step 2.
2. **Isolate.** Use `rig:scout` to trace the path. List at most 3 hypotheses, ranked, each consistent with the loop's red output; test the top one with a probe (a log line, a narrower test, one loop run with one variable changed). Never use a speculative fix.
3. **Fix** (tier L: only after the plan is approved; see step 4). If the loop is not already a regression test in the project's suite, first pin it as one and record the red run (`sdlc.ts run --expect-fail`); the fix is not done until that test exists. Apply the smallest change that makes the regression test pass and keeps the rest green; do not refactor along the way. If the fix touches more than 3 files or a contract, stop: it is a feature or refactor, so tell the person.
4. **Tier L: stop for approval before fixing.** After steps 1–2 (the failing test and the root cause), write `.rig/changes/$0/plan.md` (≤ 30 lines, no code): `## Root cause` (`path:line`, one paragraph), `## Fix` (the smallest change, in words), `## Files`, `## Verification`. Then stop and tell the person: review plan.md and run `/rig:approve $0 plan`. When run again after approval, go straight to step 3.
5. **Record (tier S and M).** Write `## Files` (touched files) and `## Verification` (test commands) into `.rig/changes/$0/plan.md`, using 15 lines or fewer and no code.
6. **Incident changes only** (`type: incident` in intent.md): the incident file is the one linked in intent.md; its date prefix is `<yyyymmdd>` and its `class:` frontmatter is `<class>`. Write `.rig/evals/incident-<yyyymmdd>-<class>.json` with the Write tool: `{"prompt": "<the incident's symptoms, one paragraph>", "base": "<the HEAD noted in step 1>", "files": ["<the regression test file>"], "checks": [{"kind": "command", "cmd": "<the regression test command>"}], "allowedTools": "Read,Grep,Glob,Edit,Write,Bash(<the regression test command>)", "source": "incident:<incident file name, e.g. 20261001-timeout.md>"}`. The source is the bare file name, with no directory. It keeps the incident in the eval suite after it ships, and runs once this change ships, when the regression test is committed. The write asks the person to approve it: eval definitions are protected. If the write is denied (headless run), give the person the JSON instead.
7. **Verify.** Run `node --disable-warning=ExperimentalWarning ${CLAUDE_PLUGIN_ROOT}/scripts/sdlc.ts verify $0` (Bash timeout 600000): it runs the plan's commands through the recorder and writes `.rig/changes/$0/verification.md`. Three failed hypotheses means consult the advisor or the person; do not keep guessing. End with: `Next: <command from status>` if verification passed, otherwise state what failed. If it passed, then keep going in this turn: run `node --disable-warning=ExperimentalWarning ${CLAUDE_PLUGIN_ROOT}/scripts/sdlc.ts skill next` and follow it, unless the person asked to stop after this stage.
