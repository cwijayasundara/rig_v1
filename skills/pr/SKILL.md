# Review, then open the PR

`S` means `node --disable-warning=ExperimentalWarning ${CLAUDE_PLUGIN_ROOT}/scripts/sdlc.ts`. The review runs on the delta only, before any PR exists.

1. Read `base` from `.rig/changes/<slug>/verify.json`. When verify is missing or failing, stop and run `/rig:test <slug>`.
2. Review once: never a second review, also not after the fixes below (the confirm pass in step 4 is not a review: it raises nothing new). Both run in the foreground. The code review is an agent launch; ask for `/security-review` in plain words in this turn (it is a bundled skill; no tool call is needed):
   - The code review, in a clean context: read `${CLAUDE_PLUGIN_ROOT}/templates/review-brief.md` and launch one `Agent` (`general-purpose`, `model: sonnet`, foreground) whose prompt is exactly that text with `<base>` and `<slug>` filled in, plus, when plan.md `## Contracts` lists a change, the line `This change edits contracts: check every changed example and schema against the code.` Also add the line `Flag any public name (function, class, method, property) the change adds that the intent's ## Design or ## Interfaces does not list.` Give it nothing else: not the plan's reasoning, not this conversation, not your own view of the code. Its answer is the code findings.
   - `/security-review all changes since <base>, committed and uncommitted, and every action in `.rig/product/architecture.md` `## Access` the change touches against its row: each allowed role enforced, every other role refused, on each interface`. Its built-in diff covers committed branch work only and is empty for this uncommitted change, so the scope must be spelled out, and the report must name the files it reviewed. It needs an `origin` remote. When it reports no `origin` remote, an empty diff, or names none of the changed files (`git status --short`), launch one `general-purpose` agent with `model: sonnet` and a brief of at most 60 lines: the base, "review only the changes since <base>, committed and uncommitted, for security: injection, authn/authz, secrets, unsafe input, crypto, path traversal, and every action in `.rig/product/architecture.md` `## Access` the change touches against its row: each allowed role enforced, every other role refused, on each interface", read-only, findings as file, line, problem, fix. Never skip the security pass.
3. Triage before you write anything. Check each code finding against `intent.md` and `spec.md`: keep it to fix, or dismiss it. A dismissal needs a reason that cites a spec line, a non-goal, or code you read that shows the reviewer was wrong; "disagree" or "out of scope" alone is not one. Never dismiss a `security`, `contract`, `design` or `unmapped` finding yourself: it stays under Findings for the person. A finding that cites a ledger id (`FR-4.2`, `G-1`) is never moved to `## Deferred` and never dismissed by you: the PRD says it, so it is fixed in the wave or stays under Findings. Keep the reviewer's category and severity exactly: never relabel a finding to dismiss it. Write the findings to `.rig/changes/<slug>/review.md`: `verdict: pass | changes-needed` (`changes-needed` exactly when `## Findings` still has an item after your triage), then `## Findings` with one line each `- [severity: critical|high|medium] [category: <slug>] path:line: problem → fix` (kept findings only), `## Dismissed` with `- path:line problem → dismissed: <reason>` and no category tag (so the learning loop counts kept findings only), `## Deferred`, `## Unverifiable` (copied from the reviewer), `## Pre-existing` (copied from the reviewer, no category tag), `## One thing`. The category is exactly one of correctness, security, contract, design, unmapped, data, coupling, responsibility, abstraction, duplication, tests; every `/security-review` finding is `security`. A `design` finding is fixed in the wave when the code is wrong. When the design doc is wrong it stays under `## Findings` (never `## Deferred`), its `→ fix` naming the sentence of the doc that should change, e.g. `→ fix: design doc §Design, "<sentence>" should read "<new sentence>" (a chart edit, which re-opens the chart approval)`; the verdict stays `changes-needed` and the PR carries it for the person. An `unmapped` finding is fixed by removing the behaviour; when the behaviour is wanted, it stays open under `## Findings` with `→ fix: design doc §Design, add "<line>" (a chart edit, which re-opens the chart approval)`, or with no design doc the intent line to add, like a doc-wrong `design` finding. Items under `## Unverifiable` are listed, never fixed, and never change the verdict. Items under `## Pre-existing` stood before `<base>`: they are listed, never fixed in this change and never change the verdict; `/rig:learn` may turn them into later intents. Style preferences and suggestions that would add what the brief's non-goals exclude go to Deferred; code that does what the non-goals exclude is a `contract` finding.
4. Run `S activate <slug>` so the hooks guard the fixes, then fix every item under `## Findings` in one wave, without asking. Fix the code, or strengthen a test the finding names; never weaken a test, a sensor or a contract file. Leave a `design` or `unmapped` finding open (unfixed, no ` → fixed`) when its fix names a design-doc sentence or line: only a chart edit can fix it, and a change never edits the design doc. Stop and tell the person, leaving that item unfixed, when a fix needs a file plan.md does not list, a frozen contract file, or a test expectation relaxed. Then update review.md to say what ships: append ` → fixed` to each line under `## Findings` you fixed (the line stays there, so the learning loop still counts it). When any line was fixed, confirm once: read `${CLAUDE_PLUGIN_ROOT}/templates/confirm-brief.md` and launch one `Agent` (`general-purpose`, `model: sonnet`, foreground) whose prompt is exactly that text with `<base>`, `<slug>` and `<findings>` (the fixed lines, numbered from 1) filled in. Rewrite each answered line's ` → fixed` to ` → fixed (confirmed)` or ` → reopened: <why>`; a reopened finding is not fixed again (there is no second wave) and stays for the person. Then set `verdict: pass` when every item under `## Findings` is now marked fixed (confirmed); a reopened finding keeps `verdict: changes-needed`, as does any item still open. Then run `S verify <slug>` (not `/rig:test`, which would hand back here). On failure fix the code and run it again; if the same check fails twice, stop and show it to the person, who may waive it with `/rig:waive`.
5. Keep the code wiki in step with the change: run `S wiki sync --max-usd 1` and quote what it prints. The first change on a repo with no `.rig/wiki.json` plans and builds the wiki; later ones rebuild only the pages whose cited code changed. It is warn-only (a `warning:` line never stops the PR), and `S pr` ships `.rig/wiki.json` and `.rig/wiki/` with the code. Never edit a page by hand.
6. Write `.rig/changes/<slug>/pr-outline.md` for the reviewer, in the person's plain words, from the diff since `<base>`: `## Special things to note` (1-3 bullets: migrations, compatibility limits, deliberate omissions, surprising decisions; `- None.` when there are none) and `## Change outline` (a compact structural view, never a file-by-file changelog: only the views that apply, such as a shallow file tree with each file's responsibility, a contract or schema change, or a changed call tree; a `diff` block for a change to an existing shape, the whole shape when most of it is new; the views are in `${CLAUDE_PLUGIN_ROOT}/templates/show-me.md`). `S pr` builds the rest of the PR body (why, behaviours, blast radius, door, risk, how to revert, what the checks would miss, evidence) from the change's files and appends this file.
7. Run `S pr <slug> --message "<type(scope): summary>"` once. It refuses without an approved plan and a fresh, passing `verify.json`; it commits the code and review.md together on `sdlc/<slug>`, pushes and opens the PR, or stays local-only without a remote. After a stop in step 4 for an unplanned file, a frozen contract file or a relaxed test, still ship review.md: revert the unfinished fix, run `S verify <slug>`, then `S pr`. After a stop for a check that failed twice, do not run `S pr`: leave review.md for the person.
8. When a PR exists, post the review with `gh pr comment --body-file .rig/changes/<slug>/review.md`, adding a line under it naming what step 4 fixed.
9. End with the PR URL (or `local-only`), what was fixed and what was left, and `Next: a person reviews and merges the PR`. Then run `S queue next`; when it names an intent (rung ≥ 1), add `Queue: <next slug> is ready; /rig:start <path>` so this session carries on.
