# Chart a sprint

`S` means `node --disable-warning=ExperimentalWarning ${CLAUDE_PLUGIN_ROOT}/scripts/sdlc.ts`. Run each command as its own Bash call.

1. **Which sprint, which PRD.** The person's PRD is accepted in any format and from any path; never reject it, ask for a template or tell the person to rewrite it. `$ARGUMENTS` may be `<N>`, `<N> <path>`, `<path>` (a leading `@` on a path is a file mention: drop it), `sprint <N>: <path>` or `.rig/product/sprints/sprint-<N>/prd.md`, any of them followed by `--convert-only` (a flag, never part of the path). `N` is the number given, else the `sprint:` in the file, else the next number after the highest sprint in `.rig/product/` (0 when there is none). If there is no PRD at `.rig/product/sprints/sprint-<N>/prd.md` and no path was given, use `docs/prd/sprint-<N>/prd.md` when it exists, else `docs/prd/sprint-<N>.md` (a `-<title>` after the number is allowed in both, as in `docs/prd/sprint-1-cart/prd.md`); otherwise stop and ask for the PRD's path. If `.rig/sensors.json` is missing, stop and tell the person to initialise a greenfield repo first, giving the stack and goal from the PRD.
   **Base commit.** The chart branch needs a base for approve, the PR and CI to diff against. If `git rev-parse --verify HEAD` fails, or `git status --porcelain .rig/sensors.json CLAUDE.md` lists either file as untracked (`??`), init's output is not committed. Do not stop: ask once with `AskUserQuestion` ("Commit init's output on main as the base for this chart?", options yes or no). On yes: with no commits, `git checkout -b main` when the current branch is not `main`, then `git add -A`; with an existing `HEAD`, `git add README.md .rig .claude CLAUDE.md` plus the scaffold paths `git status --porcelain` shows as untracked; then `git commit -m "chore: rig init scaffold"` and carry on. On no, stop and say the chart needs that base.
   **Take it as given.** Copy the person's file, unchanged, to `source.md` beside `.rig/product/sprints/sprint-<N>/prd.md` (a PRD already at that `prd.md` with no `source.md` is moved to `source.md` first); a PDF, Word or HTML original is kept as `source.<ext>` and `source.md` is its plain text. Never edit `source.md` after that. When the PRD is `prd.md` in a folder of its own (`docs/prd/sprint-<N>/` or `docs/prd/sprint-<N>-<title>/`), copy the other files in that folder unchanged to `.rig/product/sprints/sprint-<N>/attachments/` (mockups, sample payloads): they are source too, read with `source.md` by the conversion, the gap pass and the architect, and never edited. Copy it to `prd.md` and run `S prd check <N> --json`: with no finding it is already in rig's format (`${CLAUDE_PLUGIN_ROOT}/templates/prd-format.md`) and needs no conversion. On a re-run with `source.md` present, never rewrite `prd.md` or `source.md`: run `S prd status <N>` first; `converted: ready` or `not converted`: go to **Requirements ledger**; otherwise run `S prd check <N>` and `S prd map <N>`, fix their findings in one round, and go on. The gap pass and the conversion review run on the first pass only.
   **Convert.** With findings, rewrite `prd.md` in the template from `source.md`, then write `.rig/product/sprints/sprint-<N>/conversion.md`. Every rule becomes a numbered line: an `AC-n.m` under its `### FR-n` (`WHEN <trigger> THE SYSTEM SHALL <response>`, or Given/when/then, with the exact values), a `DR-n` under `## Data rules` (ids, uniqueness, ranges, what is never reused), an `NFR-n` row with its number; keep the file's own FR-n and NFR-n ids and number the rest in order, and copy every fenced example under `## Examples` unchanged. Never invent a requirement, a number or an answer; put every unclear point under `## Open questions`. `conversion.md` has one line per sentence, bullet and table body row of `source.md`, quoted word for word: `- <ids> source.md:<line> "<quote>"`, or `- context source.md:<line> "<quote>" — <why it is not a rule>`; a table row is quoted as its cells joined by " | ". A fenced block and a table header are not mapped (the block is copied under `## Examples`, which `prd map` checks), and any other note in `conversion.md` is prose, never a `-` bullet. A rule the person says is not for this sprint keeps its criterion, marked `(out of scope: <when>, decided by <who> — <reason>)`.
   **Gap pass (you, no agent).** Run it during the conversion, or on an in-format PRD. Read the PRD, `.rig/product/backlog.md` when it exists (ask each `[open]` item as a gap question, and on the answer mark it `[taken by sprint-<N>]` or `[dropped: <reason>]`), `.rig/product/brief.md`, `.rig/product/architecture.md`, `.rig/sensors.json`, the existing tests and the code files the PRD names, then list what a test could not assert yet: no technology (language, framework, the libraries it is built on such as an LLM or web framework, datastore, hosting; the architecture document names them, so ask for each the PRD leaves out), no non-functional requirements (performance, security, availability, accessibility, scale), and ambiguities that change an expected value (rounding, formats, limits, ordering, units, error text, how a number is measured), and any PRD rule that contradicts an existing test (a test that expects a behaviour the PRD changes or leaves open). An NFR target the source states as an absolute ("never", "no", "contains no") is the number 0 quoting that word, not a gap. Put them in one `AskUserQuestion` batch of at most 4 questions, each with the likely options and a free-text answer; with no gaps, skip the question. Do not ask what the PRD already states. In the same sitting, right after that batch, ask the design questions step 2 would ask (how the sprint splits into intents, an approach between real alternatives) in a second batch of at most 4, the recommended option first, so the person answers everything the chart can foresee at the start. Those design answers go into the design doc under step 2's rules ("you decide" is your recommendation marked `(decided at chart)`), never into `prd.md`. Write each answer into `.rig/product/sprints/sprint-<N>/prd.md` marked `(answered at chart)`: technology under `## Integrations and constraints`, a non-functional answer as a numbered `NFR-n` row with the person's own target, anything else as an `AC` or `DR` under the requirement it refines (a `## Decisions` bullet when it is not a rule). "You decide" is left for the architect's ADR and listed under `## Open questions`. Never invent an answer.
   **Check the conversion.** For a converted PRD, run `S prd check <N> --json` and `S prd map <N> --json` and fix every finding, one round. Then launch `rig:evaluator` in the foreground with the brief "check the conversion for sprint <N>" and write its reply to `.rig/product/sprints/sprint-<N>/conversion-review.md`; fix its findings in one round, appending ` → fixed` to each, with no second review.
   **One gate, at the end.** There is no PRD approval: `/rig:approve chart-<N>` covers `prd.md`, `source.md` and `conversion.md` with the rest of the chart, and refuses while the conversion has a finding, `prd.md` an open question or `conversion-review.md` a finding not fixed. Go straight on to the ledger and the design. Only when `$ARGUMENTS` has `--convert-only` (a person who wants to read the conversion before the decomposition): commit as step 7 does and end with: read `prd.md` beside `source.md` and `conversion-review.md`, then run `/rig:chart <N>` again to decompose it; nothing is approved yet.
   **Requirements ledger.** Run `S prd ledger <N>`: it writes `requirements.md` from the PRD's numbered criteria; never write or edit it yourself, and run it again whenever `prd.md` changes.
2. **Design.** Invoke `superpowers:brainstorming` with the PRD (and `.rig/product/brief.md`, `.rig/product/architecture.md` when they exist) as the opening material and one added line: the written design goes to `docs/superpowers/specs/<date>-sprint-<N>-design.md` and must end with `## Intents`, one line per intent as `- <slug>: <one-line scope> (<PRD ids>)`, and a `## Design` section a builder can draw `architecture.md` from. The chart runs the brainstorm in one batch, not as a conversation, because `/rig:approve chart-<N>` is the person's one review: never ask one question at a time, never present the design in sections for approval, never ask the person to review the written spec, and never invoke `superpowers:writing-plans` after it (the architect plans). List only the design choices the PRD, the gap pass answers, `brief.md` and `architecture.md` leave open and that were not already answered in the gap pass (how the sprint splits into intents, an approach between real alternatives) and ask them in one `AskUserQuestion` batch of at most 4 questions, the recommended option first; with none open, skip the question. Write each answer into the design doc as a decision, and an answer of "you decide" as your recommendation marked `(decided at chart)`. Then write the design doc and go straight on to the architect. With `.rig/wiki/index.md` present, hand the brainstorm the code wiki as recon: it reads the pages that name the files in play, trusts a page only through its `[path#symbol]` citations, and runs `S wiki status` first, treating a stale page as a hint to read the cited code, never as fact. Offer recon and `anthropic-skills:deep-research` where it offers recon. Do not continue until the design doc exists.
   **Architect.** Launch `rig:architect` in the foreground with no model override (its frontmatter sets the generator model) and a brief of at most 40 lines:
   - the PRD path, the ledger `.rig/product/sprints/sprint-<N>/requirements.md` (every behaviour cites the ledger ids it serves and keeps each number, limit and "never", "only", "unique" or start value of those rows), the design doc path, `.rig/product/brief.md` and `.rig/product/architecture.md` when they exist, and the formats `${CLAUDE_PLUGIN_ROOT}/templates/intent-format.md`, `implementation-plan-format.md` and `architecture-format.md`;
   - write `.rig/product/sprints/sprint-<N>/intents/<slug>.md` with `sprint: <N>` (slug of at least two characters, `estimate_days` 1 or 2, every behaviour citing a requirement the PRD defines, a `kind: boundary` intent naming its `Contract:` and `Example:` files), write `.rig/product/sprints/sprint-<N>/implementation-plan.md` as `implementation-plan-format.md` lays it out (one lane per engineer the PRD's `engineers:` gives, a task section per intent, `owner:` left for a person), update `architecture.md` as `architecture-format.md` lays it out (stack table, each mermaid diagram with its ASCII twin in a ```text block, code structure, a tactic per NFR, this sprint's history row), fill `brief.md`, and add ADRs under `.rig/product/adr/` with `sprint: <N>`;
   - write `design: <repo-relative path>` of the design doc into `architecture.md` frontmatter, and write one intent per line of the design doc's `## Intents`, no more and no fewer;
   - a repo file goes in the `scope:` of one intent only, unless one of the two depends on the other (`chart check` blocks a file shared by intents that can be built at the same time);
   - when the PRD names users or roles, fill `## Access` in `architecture.md`: one row per action, its allowed roles (or `nobody`), its interfaces and the intent that builds it;
   - sprint 0 always includes a `walking-skeleton` intent that every other intent depends on;
   - with code but no architecture document, read the code with read-only searches first.
   Tell it to take the check rules from the formats and the brief, never to read `.rig/bin/` (the chart runs the check and sends back its findings). When it returns, run `S chart check <N> --json` before asking anything, then put the architect's open questions and every `concern` and `open-question` finding of that check in one `AskUserQuestion` batch (at most 4, the recommended option first; skip it when there are none): this is the chart's last question. Write each answer into the sprint PRD as in the gap pass (a concern's answer goes into its `## Concerns` bullet, marked `(resolved)` with who decided), and relaunch the architect only when an answer changes an intent.
3. **Check.** `S chart check <N> --json` again once the answers are in. Each `block` finding names the rule and the file. Make at most one fix round: relaunch the architect with only those findings, then check again. Never edit the PRD to make a finding go away.
4. **QA.** Launch one `general-purpose` agent in the foreground with model `sonnet`, brief of at most 40 lines as `/rig:testplan` gives it: read the PRD, the design doc at the path the architect brief names (its reasoning and failure modes decide which cases matter), the intents, `architecture.md` and `${CLAUDE_PLUGIN_ROOT}/templates/testplan-format.md`; write `.rig/product/sprints/sprint-<N>/testplan/plan.md`, `cases.md` and `data/`; every requirement, and every `rule` and `answer` row of `requirements.md`, gets a case citing its ids (FR/NFR and ledger ids in the Requirement column), an intent slug and a B-number; for every `## Access` row of this sprint's intents, one allowed and one refused case per interface (refused only, for `nobody`), with the Access column filled as `<action>: allowed <interface>` or `<action>: refused <interface>`; data is synthetic. Then `S chart check <N> --cases --json` with at most one fix round.
5. **Review.** Launch `rig:evaluator` in the foreground with no model override and the brief "review the chart bundle for sprint <N>", plus the `chart check` output and the design doc as a source. Write its reply to `.rig/product/sprints/sprint-<N>/chart-review.md`. On `changes-needed`, make one fix round: relaunch only the generator that owns each finding (architect or QA) with just those findings, then run both checks again. A finding owns by the files it cites, not the owner it names: the architect owns intents, `implementation-plan.md`, `architecture.md`, ADRs and `docs/contracts/`, QA owns `testplan/`, and a finding citing files of both goes to both, so a fixed case never contradicts an unfixed intent line. A fix that changes a decision the design doc states also edits those lines of the design doc, so no document is left out of date. Then append ` → fixed` to each finding line the round fixed, and relaunch `rig:evaluator` once, in the foreground, with the brief "confirm the fixes for sprint <N>" and only those lines. Rewrite each line's suffix as it answers: ` → fixed (confirmed)` or ` → reopened: <why>`. Set line 1 to `verdict: pass` only when every item under `## Findings` is confirmed; leave `changes-needed` otherwise. There is no second fix round: `/rig:approve chart-<N>` refuses while a finding is not confirmed, and a person may accept one as it stands with `/rig:waive chart-<N> <finding number> <reason>`. Never edit the PRD to clear a finding.
6. **Plan view.** `S chart plan <N>` writes `.rig/product/sprints/sprint-<N>/plan.md` from the intents' `depends:` lines (waves, owners, text graph, Mermaid graph, what can start). It is generated: never edit it.
7. **Commit.** `git checkout -b rig/chart-<N>` (or `git checkout rig/chart-<N>` when it exists), `git add .rig/product docs`, `git commit -m "docs: chart sprint <N>"`.
8. End with the intents (slug, requirements, days, dependencies), the `## Graph (text)` block of `plan.md` verbatim, the `## Allocation` table of `implementation-plan.md` verbatim, the two paths `.rig/product/sprints/sprint-<N>/plan.md` (build order) and `.rig/product/sprints/sprint-<N>/implementation-plan.md` (tasks and lanes) with a line saying a person assigns engineers by filling `owner:` in each intent (it does not make the approved chart stale), the review verdict with each finding still open by its number and the line "a person fixes it or runs `/rig:waive chart-<N> <finding number> <reason>`", and `Next: review the branch (for a converted PRD, prd.md beside source.md and conversion-review.md first), then a person runs /rig:approve chart-<N>`: that one approval covers the PRD and everything the chart wrote.
