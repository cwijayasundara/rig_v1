# Build a change

`S` means `node --disable-warning=ExperimentalWarning ${CLAUDE_PLUGIN_ROOT}/scripts/sdlc.ts`.

1. Run `S status --json`. The change (`$0` or the active one) must be at `build`. At `approve`, stop: a person approves first.
2. If HEAD is the trunk, run `git checkout -b sdlc/<slug>`.
3. Read `.rig/changes/<slug>/requirements.md` when it exists: the PRD's own words for this change; never edit it, and a test asserts each row's numbers and limits as written. Tests and code come from two contexts:
   - (a) Test writer: launch one `general-purpose` agent, model `sonnet`, in the foreground, with a brief of at most 40 lines: spec.md's behaviours, requirements.md, plan.md's interfaces, the contract files, the test command, and these rules. For each behaviour in order, write the test that names its B-number and each acceptance criterion it proves: `test_ac_1_2_...`, or the id (`AC-1.2`) in the test title; `pr` refuses a change whose intent cites an AC that no test names. A test implementing a test-plan case whose Data column names a file (`data/blank-sku.json`) loads that file from the sprint's `.rig/product/sprints/sprint-<N>/testplan/data/`, unchanged, never a copy and never an inline dict. It reads interfaces only, never the bodies of source files the plan changes, and sees each test fail with `S run --expect-fail -- "<test command>"`.
   - When `intent-map.md` exists (frozen at approval; never edit it), the brief adds: write the formal checker its `## Formal command` names and the empirical tests, each scenario's test runnable with `S run`. The checker is frozen with the tests: `tests-freeze` takes its path (the first script file under `## Formal command`) from the map even when it lives outside the test paths; a checker that cannot be found that way must live under the test paths. The test writer does not run `S intent-record`, plant mutants or adjudicate: that comes after the code passes, in (c).
   - (b) Run `S tests-freeze <slug>`: it hashes the test files, their support files and fixtures, snapshots and runner config in the diff into `tests.freeze.jsonl`, and commits them (`test(<slug>): freeze tests from the test writer`) so the hand-off commit holds the tests alone; it refuses to freeze nothing when spec.md has B-numbered behaviours. The freeze is enforced once committed: from here a change to a frozen file blocks locally and in CI, however it is written, and code committed before the hand-off blocks at ship.
   - (c) Implementer (this context): write the code until `S run -- "<test command>"` passes, never editing a frozen test. A test that is wrong goes back to (a) with the reason, then run `S tests-freeze <slug> --why "<reason>"`; a frozen file leaves the set only with `--drop <file>` (repeatable), and each re-freeze and drop is listed for the reviewer and the PR needs a person. When the code passes and `intent-map.md` exists: run each scenario with `S intent-record <slug> <E-id> -- "<test command>"`, which writes `status`, `command` and `commit` itself, so never write them. Plant each clause's bug in a scratch copy, never on the branch, and list it in the checker's JSON line. A planted bug that survives is either fixed (tighten the clause, which needs a re-approval) or, when the mutant is not a bug, ruled on by a person with `S intent-adjudicate <slug> <mutant-id> non-bug --clause <C-id> --by <name> -- "<reason>"`; never write `adjudications.json` yourself.
   When `intent.md` has a `from-diff:` line the code already exists: the test writer writes each behaviour's test and runs it with `S run -- "<test command>"` to see it pass, with no `--expect-fail` step; `/rig:test`'s red-proof then runs the new tests on the base, without the captured code, where they must fail. A test that passes there proves nothing: rewrite the test, never the base.
   Touch only the files plan.md lists. If another file must change, add it under `## Decisions` in plan.md and tell the person, who re-approves. A listed test that pins behaviour this change alters is updated to the new expectation (never an assertion removed or loosened); run the whole suite, not only the new tests, before `/rig:test`.
   When plan.md has `## Phases`, finish and verify one phase before the next, tick it (`- [x]`) and, on a resumed build, start at the first unticked phase.
4. For an operation that can raise, check each step after the commit point (rename, replace, commit, send): it must not make the operation report failure once the change is in place, or the code says why.
5. The hooks run the sensors after each edit and at the end of each turn. Fix what they report; when a finding survives your fix, write in one sentence the premise that fix rested on and check it before the next fix. Never weaken a test, a sensor or a contract file.
6. For a large plan, run at most one `general-purpose` agent with model `sonnet` per independent group of files, in the foreground, each with a brief of at most 60 lines: the behaviours, the files and the test command.
7. Hidden acceptance cases run in `/rig:test`; a failure names a case id and its requirement: fix the code against that requirement. The hook that hides them is a guardrail; CI, which runs every case from the base branch, is the check.
8. When every behaviour has a passing test, continue with `/rig:test <slug>` in this turn.
